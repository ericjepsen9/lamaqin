## 三、怎么对齐 + 数据会不会丢(总负责人已定:以分支 DB 为准)

因为我们 69 张表全是裸 `CREATE TABLE`(撞已存在的表会**报错中断**),不能在现库上"边撞边跑"。正确做法 = **重建**(drop 干净 → 空库跑全套迁移),schema 100% 等于分支。

**数据影响(关键):**
| 数据 | 重建后 | 说明 |
|---|---|---|
| **讲记内容**(courses/lessons/resources/blocks/self_study/questions) | ✅ 可一键恢复 | 仓库里有 `scripts/seed-dev-from-prod.sh`,从**生产库 sss 只读拷贝**这些内容表回 sss-dev。本就是 prod 副本,无损 |
| **App/用户数据**(practices、班级、profiles、测试数据) | ⚠️ 不自动回 | 该脚本不种这些;迁移里的种子(如 practices 参考数据)会随重建自动回,**手工注入的要手动补** |
| **登录账号**(`auth.users`) | ✅ 不受影响 | 重建只动 `public` schema,`auth` 不碰;重建后补回 `profiles` 行即可 |

**安全流程(给负责执行的同事):**
1. `pg_dump` 整个 sss-dev 备份一份(兜底,可回滚)。
2. 重建:drop public → 跑分支全套迁移。
3. `seed-dev-from-prod.sh` 从 prod 重灌内容(需 prod 只读凭据 + sss-dev 凭据)。
4. 补回 App 测试数据 + `profiles` 行(status=active)。
