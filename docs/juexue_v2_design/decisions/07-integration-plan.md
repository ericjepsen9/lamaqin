# 新旧设计融合计划

> 状态：进行中
> 制定日期：2026-05-28
> 目标：将旧设计的实现细节与新设计的业务逻辑整合为可执行的融合设计文档

---

## ⚠️ 每次工作开始前必读（工作守则）

1. **本项目是文档融合，不是数据迁移。** 旧设计（FINAL_DESIGN_SANSUSHENG.md）只是设计文档，没有生产数据库，不需要考虑数据迁移策略。
2. **不改代码，不改原始设计文档。** FINAL_DESIGN_SANSUSHENG.md、DESIGN_DECISIONS.md 只读，不修改。
3. **以 20 条业务能力为验收标准。** 每张表设计完毕后，必须能明确说出它服务于哪条能力（06-business-capabilities-WIP.md）。
4. **设计分两阶段：先写，后验。** 写完全部表结构之后，用 20 条能力逐条走查，走不通就补表/补字段/修逻辑。
5. **每次会话开始前读本文件 + 06-business-capabilities-WIP.md。** 不凭印象，以文档为准。
6. **用户核对节奏：写完一个模块，贴给用户看，确认后再写入文件。**

## 一、核心判断

旧设计（FINAL_DESIGN_SANSUSHENG.md）的**技术实现层**有参考价值：47 张表的字段命名、API 模块划分。
新设计（决策档案三件套）的**业务逻辑层**是正确的：角色/权限/升学条件/传承管理。

**整合目标**：以新设计的业务逻辑为准，参考旧设计的字段命名和结构规范，产出一份字段级完整的融合设计文档，可直接用于写 Prisma schema。

---

## 二、五类表的处理方式

| 标签 | 含义 | 做法 |
|---|---|---|
| ✅ 复用 | 字段/语义与新设计一致 | 直接从旧设计复制字段，不改 |
| 🔧 扩展 | 表保留，但需加字段或改字段语义 | 旧设计字段为底，按新业务逻辑加字段/改语义 |
| 🔄 替换 | 设计思路冲突，模型根本不同 | 按新设计重写，旧表仅作命名参考 |
| ❌ 废弃 | 旧设计有但新设计明确不做 | 不纳入融合文档 |
| ➕ 新建 | 新设计需要但旧设计完全没有 | 按新业务能力从头设计字段 |

## 三、执行步骤

### 步骤 1：产出融合设计文档（进行中）

**产出顺序**（按价值和依赖关系）：

1. **🔧 扩展区（8 张）**：旧底新加，工作量最集中，先处理
2. **🔄 替换区（3 张）**：按新逻辑重写，旧设计仅作字段命名参考
3. **➕ 新建区（12 张）**：按 20 条业务能力设计字段
4. **✅ 复用区（23+ 张）**：直接搬，快速过
5. **⏸ 暂缓区（7 张）**：保留旧设计原样，打暂缓标签

**每张表的必写内容**：

```
表名：xxx
标签：✅/🔧/🔄/➕
服务能力：能力 #X（引用 06 文档）
角色权限：谁可以写（角色 + 作用域）
字段列表：字段名 | 类型 | 说明
关键约束：DB 唯一约束 / 应用层 / Zod（三选其一或组合）
业务规则：关键的不变量或状态机
```

**每张表封板时必做两件事（不得跳过）**：

1. **记录决策**：每个非显然的选择（删字段/建新表/选方案）追加到 08 文档 §八 决策记录表，写明「选定方案 + 排除方案及理由」。
2. **跑范围内一致性检查**：用 §九 的 14 项清单对「本表 + 已封板表」做一次检查，新增一轮检查记录；发现问题当轮修复。不适用项标 ⏸，依赖未就绪项标 ⬜。

> 教训（2026-05-29）：1.1~1.3 三轮只在 commit/变更记录里带过 WHY，未建文档内决策记录小节、未跑一致性检查。补建 §八/§九 时一次性回填，并发现 EnrollmentStatusHistory 缺反向关联。此后每表封板必跑，不再积压。

### 步骤 2：20 条能力走查验收

设计文档全部写完后，用 20 条业务能力逐条做路径走查：

```
能力 #X：[能力名]
触发：学员/管理员 做了什么
写入：写入哪张表的哪个字段
状态变更：触发什么状态变化（如有）
读取：管理员/系统查询时从哪张表读
升学检查：升学时这条能力如何被验证（如适用）
结论：✅ 完整 / ❌ 缺 [表/字段] / ⚠️ 逻辑待确认
```

**走查结论为 ❌ 或 ⚠️ 时，立即回到步骤 1 补充设计，不得跳过。**

### 步骤 3：一致性检查清单（提交前必跑）

在步骤 2 走查通过后，跑完整一致性检查：

**原有 8 项（来自 CLAUDE.md）**：
- □ 1. Prisma 关联对称性
- □ 2. API 响应字段与 DB 字段对齐
- □ 3. SQL 视图表名正确
- □ 4. 总览计数正确
- □ 5. Migration 覆盖完整
- □ 6. Phase 计划覆盖完整
- □ 7. 暂缓/不做标签完整
- □ 8. 业务规则约束有实现方式

**扩展 6 项（融合设计专用）**：
- □ 9. 升学条件 20 项能否全部从数据库查出（AdvancementCheck 路径完整）
- □ 10. D14（累计型/日常型）豁免逻辑有对应字段区分（`vow_type` 或等价字段）
- □ 11. D17（代行操作）留痕路径完整（AuditLog 覆盖所有代行操作类型）
- □ 12. D18（永不物理删除）每张表有 `deletedAt` 或 `status=archived` 或明确说明为何不需要
- □ 13. 02 文档 23 个职能，每个职能的"写表操作"在融合设计里有对应 API + 表
- □ 14. `source_type` / `type` 枚举值在所有引用该字段的地方定义一致

## 四、三层验收保障（设计质量约束）

### 第一层：文档结构内置约束

每张表必须注明（写入融合设计文档）：
- 服务能力编号（能力 #X）
- 写权限（哪个角色，哪个作用域）
- 业务规则的实现层（DB 约束 / 应用层 / Zod）

不允许只写字段列表，不写权限和约束。

### 第二层：能力走查（步骤 2）

20 条能力全部走通 = 设计闭合。
走不通 = 立即补设计，不允许"先写代码再看"。

### 第三层：角色权限矩阵验证

02 文档（02-roles-and-permissions-v1.md）里的 23 个职能，每个职能：
- 对应哪张表的写操作
- 用什么角色条件控制
- 在融合设计里有没有 API 路径

验证方法：对照 02 文档职能列表，逐条在融合设计里找对应的表和 API。
