## 一、4 个角色

| 代码 | 中文名 | 一句话定位 | 角色等级 |
|---|---|---|:---:|
| `class_tutor` | 班级辅导员 | 教学、讲法、答疑 | 1 |
| `class_admin` | 班级管理员 | 班级一切事务的拍板人 | 2 |
| `subject_admin` | 学科管理员 | 跨班级的学科级管理 | 3 |
| `super_admin` | 平台超级管理员 | 上帝模式,可代任何人做任何事 | 99 |

学员(`student`)是核心用户角色,不属于"管理角色"范畴。

## 二、权限继承规则

**上级角色自动拥有下级角色的全部权限**:

```
super_admin (99)
   ↑ 包含全部
subject_admin (3)
   ↑ 包含全部
class_admin (2)
   ↑ 包含全部
class_tutor (1)
```

### 含义
- 班级管理员**自动有**辅导员的所有权限(教学、出题等)
- 学科管理员**自动有**班级管理员 + 辅导员的所有权限
- 超级管理员是"上帝模式",可以做任何人能做的任何事

### 代码实现思路

```typescript
const ROLE_LEVEL = {
  class_tutor: 1,
  class_admin: 2,
  subject_admin: 3,
  super_admin: 99,
};

const PERMISSION_REQUIREMENTS = {
  'teaching.deliver': 1,           // 辅导员能做
  'class.report.approve': 2,       // 班级管理员能做
  'subject.exam.create': 3,        // 学科管理员能做
  'platform.config': 99,           // 仅超级管理员
};

function canDo(user, permission, scope) {
  const userMaxLevel = max(user.rolesInScope(scope).map(r => ROLE_LEVEL[r]));
  return userMaxLevel >= PERMISSION_REQUIREMENTS[permission];
}
```

> **JWT 承载方式（DR-114，2026-05-31）**：采**方案 B**——JWT 只留 `sub`/`sid`，**不烤 role**；鉴权时由 `permissions.ts` 按 `sub` 查 `UserRoleAssignment`（`rolesInScope` 即查库结果）+ 短 TTL 内存缓存补性能。理由：角色变更/撤销须**即时生效**（D17 代行、撤销资格、任命失效），方案 A「角色烤进 token、等过期才生效」不可接受。代价=每请求多一次查库/缓存；token 去 role 致已签发全失效需重登。详见 08 DR-114。

## 三、一人多角色 + 作用域

### 权限模型

```typescript
UserRoleAssignment {
  user_id: 'user_001',
  role: 'class_tutor',
  scope: { class_id: 'class_19_jiaxing_A' },  // 仅在该班生效
  granted_at: '2026-01-01',
  granted_by: 'user_super',
  is_active: true,
}
```

### 作用域规则

| 角色 | 必需作用域 |
|---|---|
| `class_tutor` | `class_id`(限定具体班级) |
| `class_admin` | `class_id`(限定具体班级) |
| `subject_admin` | `major_id`(限定具体专业,跨该专业所有班级和届) |
| `super_admin` | 无,全局生效 |

### 关键规则

- 一个用户可以拥有任意多条角色 assignment
- 同一个 user 可以同时是 X 班学员 + X 班辅导员(身份不互斥)
- 学科管理员管该学科的所有届(一个 `subject_admin` 管所有届的加行)
- 跨学科 / 跨班级生效需要多条 assignment

## 五、关键设计原则

### P1:班级管理员是"班级一把手"
对本班学员的**一切个体事务**有决策权,不需要上报:
- 升学审核
- 特殊身份认证
- 取消虚报资格
- 金刚萨埵替代顶礼
- 任何代行操作

### P2:学科管理员管"事",不抢班级管理员的"人"
学科管理员的核心职责是**学科本身**:
- 出官方考题
- 规范学科课程配置
- 登记传承法会
- 创建班级
- 跨班级数据统筹

### P3:超级管理员是"上帝模式"
**没有任何操作是超级管理员做不了的**。包括代任何角色做任何事。但每次操作都留痕。

### P4:学员可同时是本班的管理角色
不强制身份互斥。资深学员可一边学修一边带班。

### P5:学科管理员管多届
一个学科管理员管该学科的所有届(19、20、21...)。不为每届单独设置。

## 六、角色任命

### 谁能任命谁

```
super_admin       ← super_admin(单签即可,留痕)
subject_admin     ← super_admin
class_admin       ← subject_admin 或 super_admin
class_tutor       ← subject_admin 或 super_admin
```

### 任命留痕

每次角色变更必须写入 `role_assignment_history` 表,包括:
- 操作人
- 被授权用户
- 角色 + 作用域
- 生效/失效时间
- 理由

### 角色失效

- 角色可设过期时间(`expires_at`),到期自动失效
- 可手动撤销(立即生效)
- **但历史记录永久保留**(对应 D18:全数据保留)

## 七、对老项目的影响

### 角色迁移

| 老项目 | 新方案（DR-113 修订，2026-05-31）|
|---|---|
| `coach` | 迁移为 **`class_tutor`**(scope=classId)；**不自动给 class_admin**——行政权由 subject_admin 逐个手动补任命（过渡期辅导员暂无报数审核/邀请码/关怀等行政操作）|
| `admin` | **全部迁为 `super_admin`**，再**人工 review 降级**该降的为 subject_admin（降级前窗口期所有原 admin 暂为全局最高权限）|
| `student` | 保持不变 |

> **DR-113 修订说明**：原方案「coach→tutor+admin 双角色自动迁移」改为「coach→仅 class_tutor + 人工补 class_admin」（行政权收紧，最小权限原则）；admin 采「先升 super_admin 后人工降级」。详见 08 DR-113 + `audit/03 §9`。

### 新增角色任命

- 超级管理员先任命各学科的 `subject_admin`
- `subject_admin` 再任命/调整各班的 `class_admin`(也可保持"辅导员兼管理员"现状)

### 代码改造

老项目所有"是不是 coach""是不是 admin"的判断需要逐处审查:
- 涉及"教学"→ 改为"≥ class_tutor 等级"
- 涉及"班级行政"→ 改为"≥ class_admin 等级"
- 涉及"全平台"→ 改为"super_admin"

## 八、变更协议

- 角色定义、权限矩阵的任何变更需 `super_admin` 拍板
- 变更必须在下方"变更记录"追加
- 涉及权限收紧的变更,所有相关 `UserRoleAssignment` 需要重新审核
