## 能力 1:阶段与专业体系

### 业务意图
觉学按"预科 → 正科"两级学修体系组织学员的修学进程。预科和正科是固定的体系结构,各自包含若干**专业**(如预科的加行/净土/入行论/学经,正科的密法/修心/念佛)。每个专业的具体规则由学科管理员根据当届的学修大纲配置,系统提供配置能力,不写死任何专业。

### 业务规则
1. **阶段固定**:`preke` / `zhengke` 两个,不可新增
2. **专业可配置**:数据库表,由超级管理员后台创建,创建即生效
3. **专业带届数**:同一专业不同届可有不同规则,所以每个专业实例是"专业 × 届"
4. **专业内规则同样可配置**:课程目录、实修要求、考试范围、升学条件等都是数据
5. **专业不可删除,只可停用**:保护历史学员档案完整性

### 输入与输出
- 输入:超级管理员后台填写新专业属性(阶段、名称、届数、课程结构、实修目标、考试规则、升学条件)
- 输出:可被学员加入的专业实例

### 与其他能力的关系
- 被依赖:几乎所有能力都依赖此(学员加入、报数、考试、升学等)
- 依赖:角色与权限(谁能创建/编辑)

### 绝对约束
1. 不能把专业硬编码到代码里
2. 同一学员可在多个专业里
3. 已加入学员的专业配置一旦上线不能随意改
4. **每个专业独立维护学期时钟**：学期编号/起修日/报数节点/升学节点均按专业（`ProgramSemester` per `programId`）独立计算；多专业并行学员各专业的学期进度、聚合口径、升学预检完全独立，不跨专业合并（G1.2）

### 对老项目的影响
- 老项目"加行"只是字符串,需结构化为专业表
- 现有学员需补录阶段和专业归属
- 新增 `Program` 表（专业 × 届，08 §1.1，DR-130 定名；旧称 `majors`）；阶段变更历史由 `AdvancementRecord`（08 §3.10，升学留档含跨阶段）+ `EnrollmentStatusHistory` 承载（旧称 `stage_history`，不单建表）

## 能力 2:学员加入专业

### 业务意图
学员通过班级邀请码加入觉学的某个班级。班级隶属于特定"专业 × 届",学员加入班级后自动成为该专业该届的学员。可加入多个班级。

### 业务规则
1. **入班入口**:邀请码,不开放公开班级目录
2. **邀请码有时效性**:可设过期时间,可手动撤销;撤销/过期后不能用于新学员加入
3. **加入即归属**:学员加入班级 → 自动归属该专业该届
4. **多专业并行**:可加入多个班级,所有专业业务上完全平等
5. **主修是 UI 偏好**:学员自行设定,仅影响默认视图和提醒,不影响任何业务规则
6. **学员可在同一班同时是辅导员/管理员**:不强制身份互斥

### 输入与输出
- 输入:邀请码
- 输出:`class_enrollment` 记录、派生的 `major_enrollment`、学员档案新增学修身份

### 与其他能力的关系
- 依赖:能力 1、角色与权限
- 被依赖:几乎所有学员侧能力

### 绝对约束
1. 学员加入后,专业归属不可单方面更改(只能退出,见能力 11.业务规则#2)
2. 同一学员可同时存在多条 `major_enrollment` 记录
3. 主修字段(`primary_major_id`)可空
4. 邀请码必须带时效字段

### 对老项目的影响
- 老项目 `joinCode` 基础能力可复用
- 但可能没有时效字段,需扩展
- 老"班级"是否绑定"专业"需融合阶段确认

## 能力 3:闻思学习与圆满判定

### 业务意图
学员按所在专业的课程表逐节学习上师传法,通过"听音视频 + 看法本 + 完成思考题"达到该节课的"闻思圆满"标准。系统记录每节课的学习行为,并按学员的特殊身份切换判定路径。

### 业务规则
1. **课程归属专业**:每节课属于一个"专业 × 届"
2. **三种课程类型**:
   - `entry`:第 1 学期入门课
   - `formal`:第 2-8 学期主修课
   - `restricted`:第 2-7 学期辅助课程(限制性,不进考试)
3. **三条圆满判定路径**(按身份):

   | 身份 | 正式/入门课圆满 | 限制性课圆满 |
   |---|---|---|
   | 健全 | 听 ≥ 1 遍 + 看 ≥ 1 遍 + 答题 | 听 ≥ 1 + 看 ≥ 1 |
   | 盲/低视力/文盲 | 听 ≥ **2 遍** | 同左 |
   | 聋/听障 | 看 ≥ **2 遍** | 同左 |

4. **完整播放/翻阅才计数**:中断的不完整次数只作参考
5. **思考题处理**:特殊身份学员(盲/低视力/文盲/聋/听障)**全部豁免**思考题
6. **14 届转入学员**:对已学课程可选"重修"或"直接报圆满"
7. **多专业并行下课程独立**:不同专业的课程**不共享、不豁免**(各自完成)——数据层落实：LessonCompletion 加 `programId` 字段，`course_completion` 预检过滤 `programId=本专业`（DR-158，ISG-9 闭合）

### 输入与输出
- 输入:学习行为事件、特殊身份配置
- 输出:`learning_record`、圆满状态、闻思进度百分比

### 与其他能力的关系
- 依赖:能力 1、能力 2、特殊身份判定
- 依赖:传承管理(待编写)——某些课程听音频即接受传承
- 被依赖:报数、考试范围、升学条件

### 绝对约束
1. 圆满判定必须按身份分支,不能用统一标准
2. 盲/文盲学员思考题字段必须可空
3. 特殊身份变更后,新课按新身份判定,历史按当时身份保留
4. "完整听一遍"需明确技术定义(融合阶段定阈值)

### 对老项目的影响
- 法本阅读基础能力可复用
- 需新增"按身份切换"逻辑
- Lesson 需扩展字段(course_type、考试归属等)

## 能力 4:加行观修

### 业务意图
加行专业的核心实修之一,学员需对《前行实修法》中的 92 个修法逐一打坐观修。这是升正科密法的硬性条件之一。

### 业务规则
1. **范围**:仅加行专业必修(其他专业可自愿做不报数)
2. **修法数量**:92 个(《前行实修法》1-92)
3. **目标量(双维度)**:
   - 单修法:≥ 3 座 **且** 累计 ≥ 90 分钟
   - 总计:≥ 276 座 **且** 累计 ≥ 138 小时
   - 单座最少:≥ 30 分钟
4. **短座不合并(DR-91 修订)**:单座 < 30 分钟不单独计数、也不合并(DR-91 废弃短座合并,比大纲更严格——大纲是「可合并」非「必合并」;换取手动提交与计算的简化)
5. **长座不可拆**:单座 ≥ 30 分钟不可拆分
6. **计时规则**:仅算实际观修时间,前后念诵不计入
7. **实施周期**:第 2 学期开始,S1 可修但不报数——任务/发愿（UserPracticeVow）于起修日（S2 开始）才建立；S1 修持无对应任务可挂，不自动计入升学聚合；**S1 历史修量如需追溯计入，须由管理员走能力 5 代行追溯录入，留痕（方案 B，G1.3）**
8. **修量起算时间**:起修日(专业配置项)前不算——起修日即 S2 开始时间（Program 配置项）；任务起修日建立后，起修日前的修量只能通过能力 5 代行补录，不可自行追溯
9. **管理员代行**:支持能力 5 的全部代行操作(豁免/替代/调整等)
10. **录入方式(DR-111 / DR-143)**:观修视频/PPT 页面保留为引导内容(净资产);学员实修后**手动点「完成观修」按钮提交这一座**记一座,**不自动记录**(看视频播放度不再自动触发座数记录);**座时长纯用户手填(DR-143),确认时校验 DR-91 ≥30 分钟**;座记录走 `PracticeLog`(meditationId/durationMinutes),`UserPracticeVow` 聚合座数/时长;看视频完成排行(MeditationSession)与打坐报数各管各的、口径不统一
10b. **app-kill 续播+延迟确认(DR-143)**:观修视频播放位置 + 未确认会话标记存 **localStorage**(进程被杀不丢),重进续播到上次位置 + 若有未确认会话补弹「上次观修到 X,本座是否完成?」(选完成→接手填本座时长);同设备不跨设备,与法本/音视频同一套交互
10c. **app 外申报(DR-144)**:线下打坐的学员可在能力 9 计数模块申报观修一座(选修法 + 手填时长 + ≥30 分钟),写 `PracticeLog{meditationId,durationMinutes,source=external}`,与 app 内「完成观修」同落点、source 区分

### 输入与输出
- 输入:实修后点「完成观修」提交这一座时间(手动,不自动)
- 输出:一条 `PracticeLog` 座记录(durationMinutes ≥ 30)、`UserPracticeVow` 聚合累计进度(座数 + 时长)

### 与其他能力的关系
- 依赖:能力 1、加入加行专业、能力 5
- 被依赖:升学条件、报数

### 绝对约束
1. 30 分钟以下的座不能单独计数(DR-91:不合并,直接不计;非「必须合并」)
2. 30 分钟以上的座不可拆分
3. 进度计算双维度(座数 + 时长都达标)
4. 每个修法累计独立维护(可走能力 5 豁免/替代)
5. 数据需带时间戳(区分起修日前/后)

### 对老项目的影响
- 老项目"打卡"基础可复用
- 但 92 修法分类、双维度等是新规则(DR-91 废弃合并报数)
- **不新增 observation_records 表**:观修座记录走既有 `PracticeLog`(durationMinutes)+ `UserPracticeVow`(座数/时长聚合),DR-91/DR-111
- 观修视频/PPT 页面(Meditation/MeditationSession)保留为引导内容 + 看视频排行(净资产,与升学座数报数各管各的,DR-111)

## 能力 5:管理员代行操作(横切能力)

### 业务意图
学修体系的硬性规则是为绝大多数学员设计的,实际运营中总有特殊情况(疾病、闭关、特殊因缘等)。本能力赋予班级管理员及以上角色对学员档案进行例外处理的权力。**所有例外都永久留痕在学员档案中,双方可见**。

### 业务规则
1. **覆盖范围**:几乎所有"硬性要求"——闻思圆满、加行观修、内加行 10 万、法王祈祷文、共修出勤、考试、升学门槛、报数、留级、起修日等
2. **操作类型**:

   | 类型 | 含义 |
   |---|---|
   | 豁免 | 直接标记"已满足" |
   | 替代 | 用另一修持等价替换(如 200 万金刚萨埵替代 10 万顶礼) |
   | 调整目标 | 修改某要求的目标数值 |
   | 修正记录 | 修改已录入的数据(如发现错误) |
   | 追溯认可 | 把 App 外的修持/学习追认为有效 |

3. **谁可以操作**:
   - 班级管理员:本班学员
   - 学科管理员:本学科全部班级学员
   - 超级管理员:任何学员
   - 班级辅导员:**不能单独操作**,可"建议"管理员处理
4. **必填字段**:理由(必填)、依据(可选)、生效范围、是否通知学员(默认通知)
5. **留痕**:每次必须写入审计日志 + **永久刻入学员档案**
6. **可撤回**:可由同级或更高级别撤回,但撤回也是新记录,**原记录永不删除**
7. **频率约束**:无系统强制限制,但异常频繁会被关怀清单打标记

### 业务规则关键点(强化)

**记录的永久性与可见性**:
- 数据库层面**永不物理删除**
- UI 层面对学员**和**管理员**双方可见**
- 学员可在自己档案上看到所有代行记录的完整内容
- 即使学员毕业、升学、退出,记录跟随档案永久存在
- 设计哲学:这些豁免不是污点,是学员学修旅程的一部分

### 输入与输出
- 输入:管理员发起的代行操作 + 理由
- 输出:学员档案对应字段更新 + 审计日志条目 + 通知学员

### 与其他能力的关系
- 横切关系:几乎所有能力都依赖此提供例外口子
- 依赖:角色与权限、决策审计日志(待编写)

### 绝对约束
1. 学员不能自行豁免
2. 理由必填
3. 审计完整(所有字段都要写入)
4. **可逆（通过撤回动作）**：撤回=新记录（原记录永不删，D18）；**多层代行撤回时原生字段须检查（DR-193）**：撤回某条 proxy action 前，先查同一 `(userId,domain,targetKey)` 是否还有其他 active（未撤回）proxy action → 有则保留原生字段不回滚（另一条仍生效）；无则回滚原生字段至代行前状态
5. 不影响他人(严格作用域到单一学员)
6. **记录不可删除**:数据库永不物理删除
7. **学员可见权**:学员对自己档案上的代行记录有完整查看权

### 对老项目的影响
- 老项目大概率没有这套横切代行能力,需新建
- 可基于老项目"管理员后台"扩展
- 新增 `admin_action_log` 表 + 学员档案的豁免标记字段

## 能力 6:内加行实修(累计型实修)

### 业务意图
加行专业的另一核心实修。学员需完成 6 项内加行,每项累计达到 10 万。这是升正科密法的硬性条件之一。区别于加行观修的"座数+时长",内加行是纯计数累计。

### 业务规则
1. **范围**:仅加行专业必修
2. **6 项内加行 + 目标**:

   | 项 | 内容 | 目标 |
   |---|---|---|
   | 1 | 顶礼 | 100,000 遍 |
   | 2 | 皈依 | 100,000 遍 |
   | 3 | 发菩提心 | 100,000 遍 |
   | 4 | 百字明 | 100,000 遍 |
   | 5 | 供曼茶 | 100,000 遍 |
   | 6 | 莲师上师瑜伽(莲师心咒) | 100,000 遍 |

3. **顶礼专项规则**:
   - 大礼拜/小礼拜/交替皆可
   - 必须同步念诵法王祈祷文 10 万遍(默念或出声皆可)
   - 未念法王祈祷文 → 系统记录"欠 X 万"(实时差值=10万−累计 prayerCount,DR-95);**补足截止时点=毕业前**,但欠账后果是**不能升密法(advanced)、不影响毕业(graduated)本身**(大纲§651「否则不能进入密法」,DR-149)
   - **顶礼替代**:身体原因可申请 200 万金刚萨埵替代 10 万顶礼(走能力 5);替代后不需补法王祈祷文；⏸ **学员申请入口待定**（当前替代由管理员在能力 5 代行界面主动发起，学员无自助申请入口；入口设计待后续讨论）
   - **替代撤销与二次替代（DR-155）**：撤销替代时，心咒 vow 状态→`revoked`（不删除，D18），顶礼 vow `isSubstituted`→false；如需再次替代，系统**复用**已有的 `revoked` 心咒 vow（status→active，currentCount→0 重新起算），不新建第二条；升学预检只读 `status=active` 的心咒 vow，确保判定唯一性（R1-T5/T6/T10 闭合）

4. **仪轨合规判定(一票否决)**:
   - 顶礼必须按"加行修法"内容观想
   - 其他 5 项必须结合《开显解脱道》仪轨
   - 皈依、发菩提心、供曼茶的偈颂必须按《学修安排》要求
   - 不合规的修量作废,需重修(可走能力 5 豁免)

5. **散念/默念**:
   - 供曼茶必须正式念诵
   - 其他 5 项散念/默念有效

6. **跨专业累计共享**(对应 D14a):同项内加行在 A 专业完成 → B 专业自动满足(累计是"果",修持成立即可)

7. **修量起算时间**:同能力 4,起修日之前不算

8. **实施周期**:S2 起报数,S8 前完成

9. **管理员代行**:支持能力 5 全部操作

### 输入与输出
- 输入:实修录入(类型 + 数量 + 仪轨合规标志)
- 输出:`inner_practice_record`、6 项累计、法王祈祷文独立累计

### 与其他能力的关系
- 依赖:能力 1、加入加行、能力 5
- 被依赖:升学条件、报数

### 绝对约束
1. **法王祈祷文必须独立计数**(不能合并到顶礼计数)
2. 仪轨合规标志必填
3. 替代方案状态档案可见
4. 跨专业共享需可追溯(B 专业满足时显示"通过 A 专业达成")

### 对老项目的影响
- 老项目"打卡"基础可复用
- 6 项分类、仪轨合规、法王祈祷文配对、替代方案、跨专业共享需扩展
- 新增 `inner_practice_records` 表或扩展打卡表字段

## 能力 7:日常实修打卡(频率型实修)

### 业务意图
预科四专业各自有"日常功课"要求,学员需每天或每周完成一定的念诵/观修/读经。日常实修跨专业**不豁免**——重视"每天的精进"。

### 业务规则
1. **范围**:所有预科专业,具体要求按各专业配置
2. **当前 4 专业的典型要求**(配置示例,非硬编码):

   | 专业 | 日常功课 |
   |---|---|
   | 加行 | 无强制日常(主要是 92 修法 + 6 项 10 万) |
   | 净土 | 每日念佛号三选一:南无阿弥陀佛 5000 / 阿弥陀佛 7500 / 藏文阿弥陀佛 900 |
   | 入行论 | 二选一或并修:每周 ≥ 3 座菩提心观修 / 每日 ≥ 1000 观音心咒 |
   | 学经 | 每日 1-9 遍《心经》+ 1 遍《普贤行愿品》;可选 7 部经长期读诵 |

3. **频率类型**:`daily`(每日)/ `weekly`(每周)
4. **"三选一/二选一"的语义**:学员自选主路径,同时多选也可以但只取一种判定
5. **跨专业不豁免(核心约束)**:多专业学员**各自独立打卡**,即使要求"碰巧相同"也不豁免
6. **学经"自选功课"**:无硬要求,只记录不判圆满,不影响升学
7. **缺席容忍度**:漏打卡只是反馈,不立即惩罚;最终影响交给升学条件判定
8. **管理员代行**:支持能力 5 全部操作

### 输入与输出
- 输入:每日/每周录入打卡、路径选择
- 输出:`daily_practice_record`、连续天数、达标率、缺席日历

### 与其他能力的关系
- 依赖:能力 1、加入专业、能力 5
- 被依赖:报数、升学条件

### 绝对约束
1. **跨专业不共享**:咒语相同也不豁免(对应 D14b)
2. 路径选择是学员权利
3. 数据按日/周聚合
4. 缺席不删除已打卡数据

### 对老项目的影响
- 老项目 `PracticeProject`/`PracticeEntry` 基础可复用
- 但频率类型、路径选择、跨专业不豁免需扩展
- 扩展 `practice_entries` 表

## 能力 8:共修与出勤(网络共修为主)

### 业务意图
共修以**网络共修(Zoom)为主**。班级管理员/辅导员在 Zoom 共修过程中发布"打卡链接",学员点击链接 → 选自己头像姓名 → 完成出勤记录。轻信任、低摩擦,凭借链接时效性过滤代打卡。

### 业务规则

#### 共修类型与打卡方式

| 类型代码 | 中文名 | 打卡方式 | 链接 |
|---|---|---|---|
| `online` | 网络共修(默认) | 学员自助:点链接 → 选自己 → 确认 | 临时生成 或 课表排定(都支持) |
| `offline` | 线下共修 | 管理员/辅导员主动勾选学员 | 不需要链接 |
| `self_study` | 自学 | **不打卡**（无签到入口，不生成 group_attend 记录，不计入升学预检出勤）| 由专业配置决定是否安排此类型 |

> **DR-187**：`sessionType='self_study'` 的场次禁止提供任何签到入口（不生成 checkInToken，不开放批量勾选端点）。自学场次是个人学修排程，不属于"共修出勤"的计量范围；实现时不得为此类型场次添加签到路径。

#### 网络共修双轨发起
**方案 1:课表预排(主推)**:辅导员设定本学期共修课表,系统按课表预生成对应的 ClassSession 场次（含排期时间），但**不自动激活签到 token**。辅导员在实际开课时手动触发「生成签到 token」，token 生成即为签到窗口起点（DR-89）。

**方案 2:临时发起**:辅导员临时加场共修,App 内"临时发起"→ 当场生成链接 → 复制到 Zoom。

#### 课表的灵活管理
- 辅导员/管理员可**随时修改**课表(取消、改时间、加场)
- 修改不需要审批
- 修改后系统自动通知本班学员

#### 链接时效（DR-89）
- 签到窗口 = **token 生成时刻起**，持续 `Program.checkinGraceMinutes`（默认 30 分钟），到期自动失效
- `startAt` 字段仅用于展示，不参与窗口计算；辅导员/老师实际开课时生成 token，窗口自动对齐实际开课时间
- 窗口时长可在专业层配置（`checkinGraceMinutes`）（详见 DR-89）

#### 网络共修学员自我识别
- 点开链接 → 看到本班学员头像+姓名网格
- 学员点自己 → 确认 → 完成
- 已打卡的学员在网格上有标记
- 同一学员同一场共修只能打一次卡(幂等)

#### 线下共修打卡
- 管理员/辅导员发起线下共修 → 活动结束进入打卡页
- 显示本班学员头像网格 → 勾选到场学员 → 提交
- 一次性批量记录

#### 平台级共修场次（DR-186）
admin 可发布 `ClassSession.classId=null` 的平台级场次（全平台统一共修，如法会随讲），端点 `POST /api/admin/sessions/platform`（DR-200 B4）。

- 学员签到时，系统广播写入该学员所有 `cohortStatus='active'` 班级各一条 `StudyRecord`（classId=各班）
- 升学预检各专业独立计入；DB 唯一约束（classSessionId+userId+studyType+classId）防重复
- `paused` 状态的 ClassMember 不参与广播写入
- 取消场次（status=cancelled）不应催签（DR-185/DR-204）
- **取消后级联失效（DR-207）**：若学员已签到（StudyRecord 已广播写入），取消场次时系统批量设 `invalidatedAt`（对称回收全部班记录）；已失效记录不计入升学预检出勤；出勤详情页显示「已失效（场次已取消）」；留 AuditLog 痕迹
- **签到回包扩展（DR-209 S3-A）**：签到 API 回包新增 `checkedInClasses:[{classId,className}]`（本次写入出勤的班级）和 `skippedClasses:[{classId,className,reason:'paused'}]`（因 paused 未写入的班级）；前端签到提示改为「已为 N 个班级记录出勤」，若 skippedClasses 非空追加灰色文字「[班名]请假中，未记录」；纯 API 响应层，无新 DB 字段

#### 补卡
- 学员**不能自助补卡**
- 辅导员/管理员可任何时候补卡(常规操作)
- 选定:学员、共修场次、理由(**可选，有意设计**——AuditLog 强制写入「由XXX补卡」已是完整留痕，不必强制填写理由增加摩擦；DR-177 越权留级的理由必填是独立治理链，两者无关（DR-189）)
- **不得对已取消场次（status=cancelled）补卡（DR-208）**——补卡端点前置校验场次状态，已取消返回 409「该场次已取消，无法补卡」
- **paused 期间补录许可（DR-209 S3-B）**：学员 paused 期间错过的平台级场次，请假结束后 class_admin+ 可用同一补卡端点补录；AuditLog.reason 必填（建议格式：「请假期间补录，原因：[...]」）；补卡时不检查学员当前 cohortStatus；DR-208 场次状态校验（status ≠ cancelled）保留
- 系统记录"由 XXX 补卡",档案可见，AuditLog 强制写入（actionType=checkin_proxy）

#### 撤销出勤
- 只有班级管理员及以上可撤销已打卡(辅导员不能)
- 撤销也留痕

#### 累计与门槛
- 出勤按学员所在班级累计
- 多专业各自独立(A 班的不算 B 班)
- 留级后进入新班，旧班出勤**不自动累入**升学预检；升学预检只计当届 ClassMember 对应班级出勤（cohortStatus='active'）；前届出勤如管理员认为已满足，可走 DR-85 豁免（exempted=true，能力5代行留痕）（详见 DR-163 / DR-181）——**豁免入口在能力10升学资格预检页**（DR-188）
- 升学门槛由专业配置(如加行 93 次)

#### 代打卡的轻处理
- 系统不主动检测代打卡(短时效 + 自我识别已过滤大部分)
- 管理员可事后审查,异常情况手动撤销
- 信任为主 + 管理员审计权

#### 自学学员
- 经管理员批准后走自学模式
- **自学学员不做共修出勤统计**（自学无班级、无共修，DR-103）。如需参与共修出勤，须经邀请码加入正式班级（能力 2）

#### 管理员代行
- 支持能力 5 全部操作

### 输入与输出
- 输入:排课表 / 临时发起 / 修改课表 / 学员自助打卡 / 管理员勾选打卡 / 补卡 / 撤销 / admin 发布平台级场次（DR-186）
- 输出:`ClassSession`（场次）/ `ClassSessionSchedule`（课表模板）/ `StudyRecord`（出勤记录，广播写入各班）/ 累计次数

### 与其他能力的关系
- 依赖:能力 1、加入班级、角色权限、能力 5
- 被依赖:升学条件

### 绝对约束
1. 链接必须有时效(过期立即失效)
2. 网络共修学员自助选自己(管理员可事后撤销异常)
3. 线下共修必须管理员/辅导员勾选(学员不能自助标注)
4. 多专业各自累计
5. 网络与线下出勤同权
6. 同场共修同学员幂等
7. 学员不可自助补卡
8. 撤销出勤限管理员

### 对老项目的影响
- **复用**：`ClassSession`（已扩展 sessionType/status/checkInToken/scheduleId/classId 等字段，DR-21~25/DR-185/DR-186）
- **新建**：`ClassSessionSchedule`（课表模板层，DR-25）；`StudyRecord` 唯一约束含 classId（支持平台级广播写入，DR-186）；`StudyRecord.invalidatedAt`（场次取消级联失效标记，DR-207）
- 旧拼音表名（`gongxiu_session_schedule`/`gongxiu_session_instance`/`gongxiu_attendance`）已废弃，以 08 §三 封板表名为准（DR-206 F1 修正）

## 能力 9:学期报数

### 业务意图
学期报数是觉学学修管理的核心结算机制（PDF 第 6 页）。每学期设若干报数节点，学员在节点期内提交本学期学修记录，由班级管理员汇总核查。报数是连接"日常学修行为"与"升学资格判定"的关键环节。报数本身没有集中审核流程——学员日常随时录入，节点截止形成快照；管理员平时可见数据，节点后核实、代行修正。

### 业务规则

**1. 任务来源分两类（首要判断）**

| 类型 | 来源 | 例子 |
|---|---|---|
| 课程自带任务 | 教学大纲配置（专业级） | 法本阅读、音视频、观修、共修出勤 |
| 辅导员布置任务 | 班级辅导员手动布置（班级级） | 金刚萨埵每天 1000、大礼拜数量、修曼扎数量 |

两类任务的数量和内容可因班而异（辅导员布置任务由各班自定义）。报数逻辑对两类任务一致。

**2. 录入方式分两类（DR-143/144 重定义为 in_app / external）**

> DR-143 后 app 内完成也是「用户手动点完成」、不再自动计次；故录入方式不再按「自动/手动」分，改按**学习发生地点**分（旧「自动记录=app内看视频自动计次」举例已被 DR-143 作废）。

| 录入方式 | 场景 | 例子 |
|---|---|---|
| `in_app`（app 内确认） | 学员在 app 内看/读/听完，点「完成」确认 | app 内看视频看完点完成；app 内读法本读完点完成 |
| `external`（app 外申报） | 学员在 app 外学习，事后进计数模块按课时申报（见规则 2b） | 纸质法本读完 → 申报「第几课·看·N 遍」；线下听音频 → 申报「听·N 遍」；线下打坐 → 申报观修一座；金刚萨埵 → 手填数量 |

系统在每条记录上标注 `source`（in_app / external），供管理员核查参考——纯 external 自报是重点核查对象（规则 10 虚报治理）。

**2b. app 外学修申报入口（DR-144，服务不用 app 学习的学员）**：计数模块提供按课时申报入口，帮助线下学习者统计学习进度。
- **维度**：听(audio/video)/看(read)/观修；**答题不可申报**（随堂题交互判分，仅 app 内做）
- **可填 N 遍**：线下一周听 3 遍即填 3 → 展开成 3 条完成事件（一遍一行，供能力 3 COUNT 遍数）
- **落点**：听/看/读 → LessonCompletion(type=audio/video/read, source=external)；观修 → PracticeLog{meditationId, durationMinutes, source=external}，**须录完整信息**（选哪个修法 + 手填时长 + ≥30 分钟校验，同能力 4 / DR-91，才能进升学聚合 DR-98）
- **防刷**：纯 external 自报靠管理员核查 + 虚报治理（规则 10），与 DR-143「防刷交治理+审核」同一套

**3. 报数节点是专业配置项**：每学期报数次数（通常 2 次）和截止日期由"专业 × 届"课表配置决定（对应 D3），不写死（能力 1）。

**4. 学员随时录入，节点截止汇总**：学员日常持续录入学修数据，报数节点截止时形成本期快照。学员无需在节点期做集中"汇总提交"的额外动作，快照由系统自动生成。

**5. 学员不能修改自己已提交的记录**：录入后即生效，错误需联系管理员走能力 5「修正记录」代行操作，留痕（对应 D17）。

**6. 管理员可编辑/删除任意记录**：通过能力 5 代行，每次操作留痕，学员档案可见（对应 D17 / D18）。

**7. 多专业各自独立报数**（对应 D9）：同一学员在不同"专业 × 届"内各自独立记录，互不影响。

**8. 自学学员个人学修追踪（不做升学报数）**（DR-103）：自学学员可录入个人学修数量（念诵/观修等）作自我进度追踪（复用 PracticeLog），但**不做学期报数节点快照**（快照是升学结算机制，自学不升学）、**不做共修出勤**。如需正式报数升学，须先经邀请码加入正式班级（能力 2）。

**9. 留级期间报数继续**：数据正常累计，不中断（能力 8）。

**10. 虚报治理（分级处理）**：
- 管理员核查发现虚报 → 要求提交**书面忏悔**
- 拒绝忏悔 **或** 再次虚报 → 管理员可走角色权限职能 #14「取消虚报学员资格」
- 忏悔与资格变更均永久留痕（D18）

**11. 报数历史永久存档，双方可见**（对应 D18）：每期快照、管理员修正记录、忏悔记录全部永久保留，学员和管理员双方可见。

**12. 报数节点截止后可补录（DR-201）**：报数节点是**进度检查点而非学修死线**，截止后未完成的任务仍可补——
- **学员自助补录**：走「事后补录申报入口」（`source=external`），可指定该学修实际归属的过去日期/报数节点；
- **快照不改**：已冻结的节点快照永不因补录变化（DR-83-B），如实保留截止时点状态；
- **升学算总账**：升学预检直接查原始数据（DR-162），补录的学修计入总累计，故节点逾期**不阻断最终升学**（真正硬截止是升学预检，能力10）；
- **「学员后补」标注**：凡录入时刻晚于该学修实际归属节点截止的 external 记录，系统派生标注「学员后补」（无新字段，由 `createdAt` vs 实际归属节点推算），纳入管理员虚报核查范围（规则10），靠忏悔/取消资格治理兜底；
- **管理员代行补录**：app 外确已修持但学员无法自报的，仍可由管理员走能力5「追溯认可」补录留痕；
- **请假顺延**：疾病等正当理由可走能力11请假，报数节点截止顺延请假天数（DR-102；注意升学截止不顺延）。

### 输入与输出
- 输入：学员日常录入（自动 + 手动）、报数节点截止触发快照、管理员修正/删除操作、忏悔提交
- 输出：`practice_record`（含任务类型、录入方式、时间戳）、`semester_snapshot`（节点快照）、`report_confession`（忏悔记录）、学员档案报数历史

### 与其他能力的关系
- 依赖：能力 1（专业配置报数节点与任务规则）、能力 2（专业归属）、能力 3/4/6/7/8（数据来源）、能力 5（管理员修正/删除代行）、角色与权限（职能 #14 取消虚报资格）
- 被依赖：能力 10 考试与升学（报数节点截止是预检触发时机；DR-162 预检直接查原始表，快照不参与升学判定）、能力 14 学员关怀清单（逾期/虚报触发关怀标记）

### 绝对约束
1. 每条记录必须标注来源（`source` in_app / external，DR-144；原自动/手动），不可混淆
2. 多专业必须各自独立，不可合并汇总
3. 学员不能修改已提交记录；修改只能走管理员代行（能力 5），留痕
4. 虚报处理必须先走忏悔流程，不可跳过直接取消资格；⏸ **忏悔机制前置检查逻辑待定**（取消资格前如何验证已走忏悔流程、学员拒绝时的处理方式，待后续讨论，见 DR-84）
5. 报数历史与忏悔记录永不物理删除（D18）
6. 学员对自己的所有报数记录有完整查看权
7. 节点截止后补录不改已冻结快照（DR-83-B）；补录走原始数据、升学算总累计（DR-162）；学员自报补录（`source=external`）凡归属过去已截止节点者派生标注「学员后补」纳入核查（DR-201）；报数节点截止时点由 `ProgramSemester.reportNodeWeeks` 配置（Y3=b）

### 对老项目的影响
- 老项目有基础的打卡/进度记录，可复用为录入底层
- "任务来源两类 + 录入方式两类"的分类标签需新增
- 节点快照机制需新建
- 新增表：`semester_snapshots`（节点快照）、`report_confessions`（忏悔记录）；`practice_records` 扩展字段（任务来源类型、录入方式）

### 可能的呈现方式（仅供参考）
- 学员端：日常录入入口（按任务类型分组）+ app 外学修申报入口（按课时标记听/看/读/观修，DR-144）；节点临近推送提醒；档案内"本期报数"时间线，in_app 确认与 external 申报有视觉区分

- 档案端：逐期快照可展开，代行修正记录可见

## 能力 10:考试与升学

### 业务意图
考试是检验学员闻思成果的正式节点，升学是对完整学修旅程的系统认定。本能力定义两类考试的规则与权限、各专业的升学硬条件判定，以及预科→正科的升学审核流程。升学条件是业务层面的硬规则，多专业并行是用户层面的自由，两者不矛盾（D13）。

> **⚠️ 毕业（graduated）≠ 升密法（advanced）——核心区分（DR-149，大纲§573/§651）**：
> - **毕业** = 第八学期学制走完的**时间事件**（管理员手动批量结业、**无实修门槛**，大纲§573「第八学期结束毕业」）；走完学制即毕业，cohortStatus→`graduated`，留预科原地。
> - **升密法** = 毕业**后**申请、满足下方完整硬条件（规则 4）→ cohortStatus→`advanced`，升入正科密法。
> - **法王祈祷文 / 灌顶 / 完整内加行是「升密法」门槛、不是「毕业」门槛**（大纲§651「应在毕业前完成 10 万法王祈祷文…否则，不能进入密法」）→ 欠账学员**可毕业、不可升密法**。
> - 毕业去向：升学（→advanced）/ 留级（→held_back，规则 7）/ 转预科（退出+加入，能力 11）/ 转功德会（❌ 不做，DR-68）。

### 业务规则

**1. 考试分两类（首要判断）**

| 类型 | 出题人 | 适用范围 | 对应职能 |
|---|---|---|---|
| 随堂测验 | 班级辅导员起（职能 #11a） | 教学辅助，不直接影响升学资格 | #11a |
| 升学考 | 班级管理员起（职能 #11b） | **S5 ⏸ 待定（G1.5，S5 节点具体业务含义待大纲确认，现阶段按普通节点处理）** / S8 升学节点，影响升学资格 | #11b |

**2. 考试成绩录入**：班级管理员及以上（职能 #7）。辅导员无权录入。成绩永久留档（D18）。

**3. 升学条件是专业配置项**（对应 D3 / 能力 1）：各专业的考试合格线、实修数量门槛、出勤次数等均在"专业 × 届"配置中定义，不写死到代码。

**4. 加行升密法的硬条件（D13，不可放宽）**：

| 条件 | 判定来源 |
|---|---|
| 全部正式课程闻思圆满 | 能力 3 |
| 92 修法完成（276 座 + 138 小时） | 能力 4 |
| 6 项内加行各 10 万（含法王祈祷文 10 万） | 能力 6 |
| 共修出勤达标（门槛由专业配置） | 能力 8 |
| S8 升学考合格 | 本能力 |
| 灌顶（已接受传承） | 能力 17 |

以上全部满足才触发升学资格，缺一不可。个别条件可走能力 5 代行豁免，须留痕（D17）。

**豁免操作入口（DR-188）**：升学资格预检页（class_admin+）→ 对 `isExemptable=true` 的未通过条件旁显示「豁免」按钮 → 弹窗填豁免理由（**必填**）→ 确认 → PATCH checkResults 写 `exempted=true/exemptedBy/exemptedAt` → `overallPassed` 重算 → 写 AuditLog(`actionType=proxy_action`)。辅导员不可豁免。

**5. 系统自动预检升学资格**：报数节点截止后，系统**直接查询原始数据表**（PracticeLog / LessonCompletion / StudyRecord / ExamGrade / TransmissionRecord，DR-162）计算各条件满足情况，生成"升学资格预检报告"供管理员参考，不自动升学。SemesterSnapshot 不参与升学判定（DR-162 已解耦），仅用于报数汇总展示。

**6. 升学审核流程**：班级管理员（职能 #16）核查预检报告 → 直接拍板审核通过或驳回，无需上报。审核通过 → 写入升学记录（AdvancementRecord），学员 cohortStatus 从 `graduated`→`advanced`（升入正科对应专业，DR-149）+ 记 EnrollmentStatusHistory。

**7. 留级处理**：升学条件未满足或管理员驳回 → 学员留级。留级操作为**两步手动**：① 管理员将原班 ClassMember 的 cohortStatus 从 `graduated` 改为 `held_back`（原因必填，通知学员并显示原因）；② 管理员另发邀请码，学员用邀请码加入新届班级（走能力 2，新 ClassMember 从 `active` 开始）。

> 班级只归档，不物理删除（D19）：学员毕业或留级后原班级由管理员手动归档，历史数据完整保留，见能力 11.业务规则#4。

**8. 多专业可独立升学，互不级联**（对应 D16，DR-150/DR-151）：同一学员在多个专业均满足条件 → 各专业独立升学，互不影响；一个专业升学**不改变其他并行专业的 cohortStatus**（完全不级联）；「正科密法 + 预科净土跨阶段并存」合法；正科并存专业数量**不设上限**；升正科后`primaryProgramId`（主修）**由用户自设，系统永不自动更改**（DR-151）。

**9. 中途退出后回归**（对应 D15）：历史学修记录继续累计，升学条件判定与普通学员一致，不重置、不优待。

**10. 升学记录永久留档**（对应 D18）：升学时间、各条件满足情况、审核人、代行豁免明细全部永久保留，学员和管理员双方可见。

> ~~11. 正科在读时预科升学预检自动豁免（DR-154 G1.7-3）~~ **❌ 已撤销（R1-T14，2026-06-03）**：原设计「学员有任意 active 正科班 → 所有预科专业预检自动 bypass」作用域过宽，会让在读正科密法豁免掉并行净土预科的真实未达标，与 D9/D16 多专业独立冲突。撤销后每条预科升学线各自独立跑 6 条件，无跨专业豁免；已 `advanced` 的成员本就不进预检，无需 bypass。

### 输入与输出
- 输入：考试成绩录入、报数节点截止触发预检（预检直接查原始表，DR-162）、管理员发起升学审核动作
- 输出：`exam_result`（考试成绩）、`advancement_check`（升学资格预检报告）、`advancement_record`（升学记录，含各条件快照）

### 与其他能力的关系
- 依赖：能力 1（专业升学条件配置）、能力 3/4/6/8（升学条件判定数据原始表）、能力 9（报数节点截止是预检触发时机；预检不读快照，DR-162）、能力 5（代行豁免）、能力 17（灌顶记录）、角色与权限（职能 #7 / #11b / #16）
- 被依赖：能力 11（留级、退出、转专业）

### 绝对约束
1. 系统不自动升学，必须经 class_admin 审核确认（职能 #16）
2. 加行升密法 6 项硬条件不可因多专业并行而放宽（D13）
3. 成绩录入权限严格限于 class_admin 及以上（职能 #7）
4. 升学记录及代行豁免记录永不物理删除（D18）
5. **多专业预检独立、无跨专业豁免**（D9/D16）：每条预科升学线按 programId 各自跑 6 条件，在读正科 A 不豁免并行预科 B 的预检（R1-T14 撤销 zhengke_bypass）
6. **super_admin 可撤销误操作升学（DR-184，受限例外）**：`advanced` 为永久终态（DR-150），但 super_admin 持有唯一撤销路径（advanced→graduated），用于纠正操作失误；必填撤销原因；写 AuditLog(advancement_decision, result=revoked) 留痕；原 AdvancementRecord 保留不删（D18）；撤销后 cohortStatus 回 graduated，须重走完整升学预检方可再次升学；**class_admin 及以下无撤销权限**

### 对老项目的影响
- 老项目"无考试无结业"已推翻（05-decision-log.md §二），需全新建立考试与升学模块
- 新增表：`exam_results`、`advancement_checks`、`advancement_records`

### 可能的呈现方式（仅供参考）
- 学员端：档案内"升学进度"板块，逐条显示各升学条件满足情况
- 管理员端：升学资格预检报告列表，逐项确认后发起升学操作

## 能力 11:留级、退出、转专业

### 业务意图
学员在学修过程中可能因条件未达标而留级、主动退出某专业、或转入另一专业。本能力定义这三个场景的操作规则、记录处理方式，以及班级的生命周期管理原则。核心原则：数据永不删除，历史永远可查。

### 业务规则

**1. 留级**

- 触发条件：升学考核未通过，或管理员在能力 10 升学审核中驳回
- 留级操作为**两步手动**：① 班级管理员将原班 ClassMember 的 cohortStatus 从 `graduated` 改为 `held_back`（原因必填，通知学员并显示原因）；② 管理员另发邀请码，学员用邀请码加入新届班级（走能力 2，新 ClassMember 从 `active` 开始）
- 原班级的学修记录完整保留，新班级继续累计；新班级的起修日、课表等按新届配置计算
- 留级记录永久留档（D18），学员档案可见

> **留级后三类指标继承规则**（DR-181，统一成文）：
>
> | 指标 | 留级后行为 | 设计依据 |
> |---|---|---|
> | 心咒 / 顶礼 累计（cumulative_count）| **保留**：全量历史聚合，不清零 | 念成的功德不因留级倒扣（DR-170 / DR-157）|
> | 92修法（practice_session）| **重算**：新 vow 起修日后打卡才计入升学预检 | 起修日界定修行起点，留级 = 重新开始修（DR-161）|
> | 共修出勤（attendance）| **重算**：只计新届 active 班级出勤，前届不累入 | 出勤是班级归属事件，换班自然重算（DR-163）|
>
> 三类口径差别是有意设计，非 bug。**实现时三类必须口径一致，不允许个别调整**。学员侧留级后进度页有横幅说明（DR-180）；管理员执行退出操作时确认弹窗含文案提示（DR-179）。

**2. 退出专业**

- **操作人**：学员自主在 app 操作，无需管理员审批
- **记录处理**（对应 D15）：退出后所有历史记录保留且学员仍可查看（只读）；回归后记录继续累计，不重置
  - ⚠️ **「继续累计」= 数据保留层（记录不删），≠ 升学预检全部接续**：回归后升学预检口径与留级相同——心咒/顶礼 cumulative_count 接续历史全量，92修法 practice_session 从新 vow 起修日重算，共修出勤 attendance 只计新届 active 班级。详见上方「留级后三类指标继承规则」（DR-181）。
- **缺席期间的空缺**：日常打卡缺口客观存在、不补填；共修出勤缺场已错过，可走能力 5 由管理员补卡（代行留痕）
- **退出状态标记**：该专业在学员档案里显示为"已退出"，不影响其他在修专业
- **回归方式**：通过邀请码重新加入班级（走能力 2），记录自动恢复衔接

**3. 转专业**

- 转专业 = **退出当前专业 + 加入另一专业**，分两步走，无特殊平移操作
- 两段历史各自独立：加行的学修记录属于加行，净土的学修记录属于净土，互不合并
- 跨专业累计共享规则仍适用（D14a）：若两个专业有相同的累计型实修，共享豁免正常生效

**4. 班级生命周期（归档原则）**（对应 D19）

- 班级**不可物理删除**：班级承载学员出勤、报数、成绩等大量历史事件，删除会破坏数据完整性并违反 D18
- 班级只能**归档**（`status: archived`）：归档后不接受新学员加入，不产生新的课表和出勤，但所有历史数据完整保留，管理端可查
- 归档触发时机：本届所有学员升学或退出后，由管理员手动归档（不自动触发）

**5. 操作留痕**（对应 D17 / D18）

- 留级、退出、转专业均永久记录在学员档案中
- 管理员代行的补卡、调整一并留痕
- 所有记录学员和管理员双方可见

**6. 取消资格（disqualified）下游**（对应 DR-152）

取消资格由能力 9 虚报处理（职能 #14）触发，`cohortStatus` 写 `disqualified`，下游规则与自主退出（`left`）不同：

- **① App 访问权限**：可继续登录，可查看自己的历史报数/学修档案（D18 全数据保留），但**失去班级成员权限**——不可进班级主页、课程内容、参与报数/出勤等班级活动
- **② 再入学条件（DR-156 D1）**：允许再入学，但比 `left` 更严——须 `super_admin` 审批 + **super_admin 书面背书忏悔确认**（审批时必填「忏悔确认说明」文字字段，写入 AuditLog 永久留档，super_admin 对结果负责）+ 管理员发邀请码，学员用邀请码重新加班（走能力 2）；系统**不做自动 gate 检查**（不依赖 DR-84，两者解耦；DR-84 取消资格前置 gate 继续 ⏸ 待定）
- **③ 历史记录处理（DR-156 D2）**：两层视图，数据不重置，时间窗口隔离——**档案视图（D18）**：历史所有打卡/闻思/考试/升学记录全部保留，学员与管理员双方可见，永不删除；**本期升学进度（从 0 重算）**：再入学时系统建新 ClassMember（邀请码落班，能力 2）+ 新 program_task vow（起始日=新入班日）；升学预检只计入新 vow 对应的 PracticeLog（vowId 隔离，DR-153）；旧 vow 打卡不计入新轮升学条件；学员端进度页默认显示本期（新 vow 进度），档案页可查完整历史

### 输入与输出
- 输入：学员发起退出操作、管理员手动添加留级学员到新班级、管理员手动触发班级归档
- 输出：`enrollment_status` 变更记录（exited / retained / transferred）、`class_status` 变更为 `archived`

### 与其他能力的关系
- 依赖：能力 2（留级/回归走邀请码加入）、能力 5（缺席期间补卡代行）、能力 10（留级由升学未通过触发）
- 被依赖：能力 9（留级学员在新班级继续报数）、能力 10（留级后重新参与升学判定）

### 绝对约束
1. 班级只归档，不物理删除（D19）
2. 退出后历史记录保留且学员可查（D15 / D18）
3. 转专业无平移操作，两段历史各自独立
4. 留级必须手动操作，系统不自动处理
5. 所有状态变更永久留档，不可删除（D18）
6. 取消资格（disqualified）下游：可登录查历史、再入学须 super_admin 审批+书面背书忏悔确认（AuditLog 留档，不依赖 DR-84 gate）+邀请码；档案永久保留+本期升学新 vow 起算（DR-156）

### 对老项目的影响
- 老项目班级可能有删除操作，需改为归档
- `class_enrollment` 表 `status` 字段重构为 08 `ClassMember.cohortStatus`（权威值域 7 态：active/paused/held_back/graduated/advanced/disqualified/left，见 08 §1.2 / DR-149；旧占位 active/exited/graduated 三值作废）
- 新增 `enrollment_status_history` 记录退出/回归/留级变更

### 可能的呈现方式（仅供参考）
- 学员端：专业列表里"已退出"专业灰显可展开查看历史；退出操作有二次确认
- 管理员端：留级操作入口在升学审核驳回后提示；班级归档操作在班级设置页

## 能力 12:特殊身份学员关怀

### 业务意图
针对两类有客观学修障碍的学员——**盲人**和**聋人**——提供两个层面的支持：① 系统层面：自动切换闻思圆满判定路径；② 人工层面：辅导员主动与师兄联系互动，跟进学修状态并留下记录。其他特殊情况不在本能力范围内，走能力 5 针对性豁免。

### 业务规则

**1. 特殊身份仅两类**

| 身份代码 | 中文 | 核心障碍 |
|---|---|---|
| `blind` | 盲人 | 无法阅读法本/字幕 |
| `deaf` | 聋人 | 无法收听音频/视频声音 |

其他任何特殊情况不认定为系统特殊身份，一律走能力 5 管理员代行豁免。

**2. 认定与变更**：班级管理员认定（职能 #13「学员特殊身份变更认证」），认定后即时生效。认定可撤销（如认定有误），撤销后恢复普通路径，历史记录按当时身份保留（D18）。认定/变更/撤销均永久留痕。

**3. 闻思圆满路径自动切换**（对应能力 3）：

| 身份 | 正式课/入门课圆满条件 | 限制性课圆满条件 | 思考题 |
|---|---|---|---|
| 普通学员 | 听 ≥ 1 遍 + 看 ≥ 1 遍 + 答题 | 听 ≥ 1 + 看 ≥ 1 | 必须完成 |
| 盲人 | 听 ≥ **2 遍** | 听 ≥ 2 遍 | **全部豁免** |
| 聋人 | 看 ≥ **2 遍** | 看 ≥ 2 遍 | **全部豁免** |

身份变更不追溯历史记录；变更后新课按新身份判定。

**4. 辅导员关怀流程（人工层面）**

- 特殊身份认定后，该学员自动出现在辅导员的关怀跟进列表
- 辅导员主动与师兄联系互动，了解学修进展、实修困难、生活状态
- 每次互动后在 app 内记录：联系时间、跟进内容摘要、师兄当前状态、下次计划（可选）
- 跟进记录属于内部工作日志：辅导员填写、管理员可查，**师兄不可见**
- 无强制跟进频率，辅导员根据师兄实际情况自行判断

**5. 辅助员配对**：特殊身份学员可配对辅助员协助学修，见能力 13。

### 输入与输出
- 输入：管理员认定/变更/撤销特殊身份、辅导员填写跟进记录
- 输出：`student_special_status`（身份记录）、`care_followup_records`（关怀跟进记录，含联系时间、内容摘要、状态、来源类型）

### 与其他能力的关系
- 依赖：角色与权限（职能 #13 认定）、能力 5（其他情况走豁免）
- 被依赖：能力 3（闻思路径按身份分支）、能力 13（辅助员配对前提）、能力 14（特殊身份学员自动进入关怀清单）

### 绝对约束
1. 特殊身份只有 `blind` / `deaf` 两种，不可扩展
2. 其他特殊情况不走本能力，一律走能力 5
3. 认定权限严格限于 class_admin 及以上（职能 #13「学员特殊身份变更认证」）
4. 身份变更不追溯历史记录（D18）
5. 跟进记录辅导员/管理员可见，**师兄不可见**（内部工作日志）
6. 认定/变更/撤销永久留档（D18）

### 对老项目的影响
- 新增 `student_special_status` 表
- 新增 `care_followup_records` 表（与能力 14 共用，`source_type` 字段区分来源）

### 可能的呈现方式（仅供参考）
- 辅导员端：关怀跟进列表，显示所有特殊身份学员；点入填写本次跟进记录
- 管理员端：可查看本班特殊身份学员及跟进历史
- 师兄端：档案里显示已认定的特殊身份，闻思进度按调整后路径展示（跟进日志不展示）

## 能力 13:辅助员配对

### 业务意图
辅助员是由班级管理员指定、负责整个班级学修辅助工作的角色。辅助员不属于四大管理角色，而是持有 class_admin 委托权限的班级成员，协助辅导员推进全班的日常学修活动。辅导员同样对全班所有学员负有跟进关怀责任（详见能力 14）。

### 业务规则

**1. 辅助员的身份定位**
- 不属于四大管理角色，是 class_admin 授权的委托性角色
- 作用域：本班全体学员
- 权限由 class_admin 授予，随时可收回

**2. 配对与授权流程**
- 班级管理员发起指定并授予权限（职能 #19「配对辅助员」）
- 辅导员（class_tutor）对配对操作只有只读权（R），无法自行授权
- 配对记录永久留档（D18）

**3. 辅助员的操作权限范围**

| 权限 | 说明 |
|---|---|
| 发起共修 | 为全班发起或安排共修场次 |
| 发起班级法会 | 组织班级法会（限本班·不计出勤·可发愿；落点能力46 `POST /api/coach/classes/:id/assemblies`，DR-203）|
| 发布任务 | 向全班发布学修任务（如念咒数量要求） |
| 监督学习 | 查看全班学员学修进度（只读） |

**4. 辅助员不能做的事**
- 不能编辑或删除任何学员数据
- 不能认定/变更特殊身份（能力 12 / 职能 #13，class_admin 专属）
- 不能审核报数、批准升学

**5. 权限收回与解除**
- class_admin 可随时收回权限，立即生效，永久留痕（D17 / D18）

**6. 辅导员的全班跟进责任**
- 辅导员对本班所有学员（普通 + 特殊身份）均负有主动关怀跟进责任
- 辅助员协助辅导员推进学修活动，但跟进关怀的主责在辅导员
- 全班关怀清单机制见能力 14

### 输入与输出
- 输入：class_admin 发起指定及授权操作
- 输出：`assistant_assignment`（配对记录，含权限范围、生效/失效时间）

### 与其他能力的关系
- 依赖：角色与权限（职能 #19 配对授权）
- 被依赖：能力 8（辅助员可发起共修）、能力 9（辅助员发布的任务进报数）、能力 14（辅导员全班关怀跟进展开）

### 绝对约束
1. 辅助员作用域为本班全体，不能操作其他班数据
2. 辅助员不能编辑或删除任何学员数据
3. 配对与授权均由 class_admin 完成（职能 #19）
4. 配对记录、权限授予/收回永久留档（D18）

### 对老项目的影响
- 老项目无辅助员概念，需全新建立
- 新增 `assistant_assignments` 表

### 可能的呈现方式（仅供参考）
- 管理员端：班级设置页「指定辅助员」，可查当前辅助员及权限状态
- 辅助员端：班级学修视图，含全班进度查看、任务发布、共修发起入口

## 能力 14:学员关怀清单

### 业务意图
学员关怀清单是辅导员日常工作的核心工具。系统自动将未按要求完成学修任务的学员标记并汇聚到清单中，辅导员据此主动联系学员、督促跟进，并留下备注记录。清单是"系统发现问题 → 人工跟进处理"的桥梁。

### 业务规则

**1. 自动触发条件**：以下任一情况触发关怀标记，学员自动进入清单：

| 触发场景 | 来源能力 |
|---|---|
| 日常功课连续未打卡（达阈值） | 能力 7 |
| 共修出勤不足（低于专业配置门槛） | 能力 8 |
| 报数节点逾期未提交 | 能力 9 |
| 虚报被管理员标记 | 能力 9 |
| 闻思进度明显滞后（达阈值） | 能力 3 |
| 特殊身份学员（盲人/聋人） | 能力 12 |

触发阈值由专业配置决定（对应 D3），不写死到代码。

> **study_lag 触发维度（DR-198）**：CohortLagSnapshot 的 `contentLag`/`quizLag`/`meditationLag` 三维**任一** not on_track → 每日 cron 触发 `study_lag` 清单条目；三维均属能力3闻思范畴（闻思内容·答题·观修），触发统一用 study_lag，快照5维分列展示供辅导员判断具体滞后维度。`attendanceLag`→`attendance_low`；`taskLag`→`practice_lag`（DR-167）；`report_overdue`/`false_report`/`special_status` 不经 CohortLagSnapshot（来自能力9/12直接触发）。

**2. 手动添加**：辅导员及以上可手动将任意学员加入清单，填写原因。

**3. 清单可见范围**：辅导员及以上（class_tutor / class_admin / subject_admin / super_admin）均可查看本班关怀清单；作用域按角色权限范围生效（D8）。

**4. 辅导员操作流程**：
- 在清单中看到待跟进学员及触发原因
- 主动联系或督促该学员
- 在清单条目上填写备注（联系情况、学员状态、后续计划）
- 可将条目标记为「已跟进」（不等于问题已解决，只是记录本次跟进动作）

**5. 自动移除与持续标记**：
- 触发条件解除（如学员补完打卡、出勤达标）→ 系统自动移除对应标记
- 多个触发条件叠加 → 清单显示全部原因，逐条解除
- 虚报标记由管理员手动移除（不自动）
- 手动添加的条目由添加人或更高级别手动移除

**6. 备注记录**：
- 辅导员填写的备注为内部工作日志
- 辅导员及以上可见，**学员不可见**
- 永久留档（D18）

### 输入与输出
- 输入：各能力触发的关怀信号、手动添加操作、辅导员填写备注/标记已跟进
- 输出：`care_watchlist_items`（清单条目，含学员、触发原因、触发时间、跟进状态）、`care_followup_records`（跟进备注，与能力 12 共用，`source_type` 字段区分来源）

### 与其他能力的关系
- 依赖：能力 3/7/8/9/12（触发信号来源）、能力 13（辅助员协助辅导员落实跟进）
- 被依赖：无（终端能力）

### 绝对约束
1. 触发阈值是专业配置项，不写死（D3）
2. 备注为内部日志，学员不可见
3. 备注及跟进记录永久留档（D18）
4. 虚报标记不自动移除，需管理员手动处理（对应能力 9 虚报治理）

### 对老项目的影响
- 老项目可能无系统化关怀清单，需新建
- 新增 `care_watchlist_items` 表
- `care_followup_records` 表与能力 12 共用（`source_type` 字段区分：特殊身份跟进 vs 关怀清单备注）

### 可能的呈现方式（仅供参考）
- 辅导员端：「关怀清单」tab，按触发原因分组或按学员汇总；点入填写备注、标记已跟进
- 管理员端：可查看本班清单全貌及历史跟进记录

## 能力 15:传承管理

### 业务意图
传承是学修合法性的根基（D4）。系统需要记录学员已接受的所有传承，并区分"升学必需传承"与"额外传承"，保护毕业门槛的严肃性。所有专业都需要传承，传承来源有三种：课程自动触发、法会、上师单独传授/灌顶。

### 业务规则

**1. 传承来源三种**

| 来源 | 触发方式 | 录入方式 |
|---|---|---|
| 课程传承 | 学员听完特定课程音频/视频（DR-143 后「听完」=用户手动确认） | 据能力 3 完成事件自动派生传承（完成事件本身手动确认，派生仍自动） |
| 法会传承 | 参加传承法会 | 学员自行申报 或 管理员/辅导员录入（传承法会不单独建立能力，直接走本能力录入）|
| 单独传授/灌顶 | 上师单独传授或灌顶 | 学员自行申报 或 管理员/辅导员录入（详见能力 17） |

**2. 传承分两类（首要判断）**

| 类型 | 定义 | 升学影响 |
|---|---|---|
| 固定清单传承 | 专业配置定义的必需传承（对应 D3） | ✓ 自动计入升学资格判定 |
| 额外传承 | 辅导员/管理员自行判断添加的传承 | ❌ 不自动计入升学 |

额外传承只作档案记录，若需用来替代某项固定传承要求，必须走能力 5 代行，留痕（D17）。

**3. 手动录入默认为额外传承**：学员自行申报或管理员录入的传承，默认归为"额外传承"。如需认定为固定清单项的满足记录，需管理员确认升格。

**4. 课程传承（提示确认，非静默自动）（DR-199）**：某些课程在专业配置中标注"含传承"。学员完成该课程的完整收听/替代方式（能力 3 圆满判定通过）→ 系统弹出提示「此课含传承（[课名]），是否已接受传承？」→ 学员点「是」后写入传承记录（`entryMethod=auto, isConfirmed=true`，**无需管理员审核**）；点「否」不写入（可稍后自行申报）。**盲人/聋人**：同等适用能力 3/12 特殊完成标准（替代方式完成即可触发提示）；若课程完全无该用户可完成的方式（如纯音频课对聋人），提示不触发，由管理员走代录路径（规则 1 代录）。

**5. 法会传承**：无系统自动触发。学员在 app 自行申报参与，或由管理员录入。传承法会**手动录入记录可以做**，统一走本能力录入流程；传承法会作为独立系统功能（自动批量登记）❌ 不做（见能力 16）。

**6. 升学判定**：升学资格预检（能力 10）自动核查固定清单传承是否全部满足，缺项不通过。

**7. 灌顶**：灌顶是一种特殊传承，是加行升密法的硬条件之一（D13），见能力 17 详述。

**8. 传承记录永久留档**（D18）：所有传承记录（含来源、类型、录入人、时间）永久保留，学员和管理员双方可见。

### 输入与输出
- 输入：课程圆满触发自动传承、学员自行申报、管理员录入/确认/批量登记
- 输出：`transmission_record`（传承记录，含来源类型、传承名称、接受时间、录入方式、是否为固定清单项）

### 与其他能力的关系
- 依赖：能力 3（课程收听触发传承）、能力 5（额外传承替代固定项需代行）、能力 17（灌顶是特殊传承）
- 被依赖：能力 10（升学资格判定核查固定传承清单）

### 绝对约束
1. 固定清单传承由专业配置定义，辅导员不可自行添加为必需项（D3）
2. 额外传承不自动计入升学
3. 额外传承替代固定项必须走能力 5 代行，留痕（D17）
4. 传承记录永不物理删除（D18）
5. 手动录入默认为额外传承，升格需管理员确认

### 对老项目的影响
- 老项目第 10 条"传承 不做"已推翻（D4），需全新建立
- 新增 `transmission_records` 表（含 `source_type`、`is_required`、`entry_method` 字段）
- 专业配置（能力 1）需扩展传承清单字段

### 可能的呈现方式（仅供参考）
- 学员端：档案内「传承记录」列表，固定传承与额外传承分组展示；手动申报入口
- 管理员端：确认手动申报记录；查看全班传承达标情况

## 能力 17:灌顶记录

### 业务意图
灌顶是藏传佛教修学中接受上师传授密法权力的仪式，是加行升密法的硬性条件之一（D13）。系统需记录学员已接受的灌顶，供升学资格判定使用。灌顶记录属于能力 15 传承管理的特殊子类，录入方式与其他传承一致：用户自行申报，管理员可代录。

### 业务规则
1. **录入方式**：用户自行申报（传承名称、日期、传授上师）；管理员/辅导员可代录。无系统自动触发。
2. **归属传承体系**：灌顶复用 `transmission_records` 表，`type = empowerment`（灌顶）。固定清单中指定的必需灌顶自动计入升学资格判定，其余归为额外传承记录（对应能力 15 分类规则）。
3. **升学硬条件（D13）**：加行专业升密法须完成专业配置指定的灌顶项目，升学资格预检（能力 10）自动核查，缺项不通过。其他专业的灌顶要求由各专业配置决定（D3）。
4. **不可随意替代**：灌顶不可用其他修持替代，除非走能力 5 代行豁免，须留痕（D17）。
5. **记录永久留档**（D18）：所有灌顶记录（含申报人、录入时间、传授上师、是否为必需项）永久保留，学员和管理员双方可见。

### 输入与输出
- 输入：学员自行申报（传承名称、日期、传授上师）；管理员/辅导员代录
- 输出：`transmission_record`（`type = empowerment`，含 `is_required` 标志）

### 与其他能力的关系
- 依赖：能力 15（归属传承体系，复用 `transmission_records` 表）、能力 5（不可替代，豁免必须走代行）
- 被依赖：能力 10（升学资格预检核查必需灌顶是否满足）

### 绝对约束
1. 复用能力 15 的 `transmission_records` 表，`type = empowerment`，**不单独建表**
2. 灌顶不可替代（能力 5 代行豁免除外，须留痕）
3. 记录永不物理删除（D18）

### 对老项目的影响
- 老项目无灌顶记录；需在 `transmission_records` 表内扩展 `type` 字段支持 `empowerment`

### 可能的呈现方式（仅供参考）
- 学员端：档案内「传承记录」列表中灌顶独立标注；手动申报入口
- 管理员端：升学预检中显示灌顶满足情况；代录入口

## 能力 18:角色与权限

### 业务意图
系统依托 4 个管理角色实现全平台权限管控，采用扁平化权限继承设计：上级角色自动拥有下级所有权限。每条角色分配都绑定作用域，防止越权操作。完整权限矩阵见 `docs/_handoff/decisions/02-roles-and-permissions-v1.md`。

### 业务规则

**1. 4 个管理角色与等级**

| 角色 | 等级 | 定位 |
|---|:---:|---|
| class_tutor | 1 | 教学、答疑、补打卡 |
| class_admin | 2 | 班级一切行政决策的拍板人 |
| subject_admin | 3 | 跨班级的学科级管理 |
| super_admin | 99 | 上帝模式，可代任何人做任何事 |

student（学员）是核心用户角色，不属于管理角色体系。

**2. 权限继承**：上级角色自动拥有下级全部权限，代码实现通过角色等级数值比较（`userLevel >= requiredLevel`）。

**3. 作用域（scope）**：
- class_tutor / class_admin → 限定 `class_id`（单班生效）
- subject_admin → 限定 `major_id`（覆盖该学科全部届、全部班）
- super_admin → 无作用域限制，全局生效

**4. 一人多角色**：同一用户可持有多条角色 assignment（如既是 A 班辅导员，又是加行学科管理员），各条独立生效。

**5. 角色任命链**：
- super_admin ← super_admin（单签留痕）
- subject_admin ← super_admin
- class_admin / class_tutor ← subject_admin 或 super_admin

**6. 任命留痕**：所有角色变更写入 `role_assignment_history`，永久留档（D18）。

**7. ~~角色可设过期时间~~** ❌ 废弃（2026-06-01 决策 B，09 设计核对发现 08 `UserRoleAssignment` 无 `expiresAt` 字段、线上无过期需求）：角色**不设自动过期**，仅手动撤销（revoke，status='revoked'）；历史记录永久保留（D18）。

**8. 学员可同时是管理角色**：不强制身份互斥（P4）。

**9. 三端入口显示逻辑（DR-191）**：`/api/auth/me` 响应包含 `roles:[{role,classId?,programId?}]`（用户全部 active assignment 精简列表）；前端按此决定显示哪些端的入口：有 class_tutor+ → 显示辅导员端（/coach/*）入口；有 subject_admin+ → 显示 admin 端（/admin/*）入口；两者可同时显示（P4）；后端路由守卫按 classId/programId 作用域即时查 UserRoleAssignment（DR-114，JWT 不烤 role）。

### 输入与输出
- 输入：super_admin / subject_admin 发起角色任命或撤销
- 输出：`user_role_assignments`（角色分配记录）、`role_assignment_history`（变更留痕）

### 与其他能力的关系
- 被所有能力依赖：几乎每条能力的操作权限都依赖本体系
- 依赖：无上游依赖

### 绝对约束
1. 权限判定必须基于角色等级数值，不能硬编码角色名称
2. 每条角色 assignment 必须带作用域字段
3. 所有角色变更永久留痕，不可删除（D18）
4. class_tutor 不能自行授权他人（职能 #19 授权权只限 class_admin 及以上）
5. 角色任命/撤销必须**双写**：`RoleAssignmentHistory`（流水账，快查单人角色变更史）+ `AuditLog(actionType=role_assignment)`（跨能力统一审计，按作用域过滤）；两者职责不同，均不可省略（DR-192）
6. **super_admin 专属操作集中清单（DR-190）**：以下操作仅 super_admin 可执行，class_admin 及以下调用须返回 403：
   - 创建/修改/停用专业（职能 #18；09 能力1 API）
   - 平台级配置/AI 配置中心（职能 #20）
   - 撤销升学（advanced→graduated，DR-184）
   - disqualified 学员再入学审批（DR-152）
   - 再入学书面背书忏悔确认（DR-156 D1）

## 能力 19:班级邀请码

### 业务意图
邀请码是学员加入班级的唯一入口（D11）。管理员生成带时效的邀请码，学员凭码加入，系统验证有效性后完成入班。邀请码通过时效性和手动撤销两道机制防止滥用。

### 业务规则

**1. 生成权限**：班级管理员及以上（职能 #5「班级邀请码管理」），辅导员只读（R）。

**2. 码的属性**

| 字段 | 说明 |
|---|---|
| 邀请码字符串 | 唯一、随机生成 |
| 归属班级 | 固定绑定一个 class_id |
| 过期时间 | 必填，管理员自定（如 7 天、30 天） |
| 状态 | active / revoked（**expired 实时算、不入库**——DB status 只存 active/revoked，过期由 `now() > expiresAt` 实时判定，DR-80） |
| 使用次数限制 | 可选（留空则不限人数） |

**3. 使用流程**：学员输入或扫描邀请码 → 系统校验（未过期 + 未撤销 + 未超次数限制）→ 通过则写入 class_enrollment，学员加入班级。

**4. 幂等**：同一学员同一班级只能有一条有效 enrollment，重复使用有效邀请码不创建重复记录。

**5. 撤销**：管理员可随时手动撤销（状态改为 `revoked`），立即生效；**已加入的学员不受影响**，只影响后续使用。

**6. 过期不影响已加入学员**：邀请码过期或撤销，只影响新加入，不影响已持有 enrollment 的学员。

**7. 码不可复用**：撤销或过期的邀请码不能重新激活，需重新生成。

**8. 操作留痕**：生成、撤销均写入日志，永久保留（D18）。

### 输入与输出
- 输入：管理员生成邀请码（设过期时间 + 可选使用次数限制）、学员使用邀请码加入、管理员撤销邀请码
- 输出：`class_invite_codes`（邀请码记录）、`class_enrollment`（学员加入记录，见能力 2）

### 与其他能力的关系
- 依赖：角色与权限（职能 #5 生成权限）
- 被依赖：能力 2（加入班级唯一入口）、能力 11（留级/回归走邀请码重新加入）

### 绝对约束
1. 邀请码必须有过期时间，不允许永久有效码
2. 撤销/过期只影响新加入，不影响已加入学员
3. 使用次数限制（max_uses）达到上限后也只影响新加入，不影响已加入学员
4. 同一学员同一班级的 enrollment 幂等，不重复创建
5. 生成和撤销操作永久留痕（D18）

### 对老项目的影响
- 老项目 `joinCode` 基础可复用，需扩展：`expires_at`、`status`、`max_uses` / `used_count` 字段
- 扩展或重建 `class_invite_codes` 表

## 能力 20:决策审计日志

### 业务意图
系统中存在大量高权限操作——代行豁免、角色任命、成绩录入、升学审核、撤销出勤等。审计日志统一记录这类操作的"谁、在什么时间、对谁、做了什么、理由是什么"，是 D18（全数据保留）的底层基础设施。

### 业务规则

**1. 覆盖范围**：以下操作类型必须写入审计日志：

| 操作类型 | 来源能力 |
|---|---|
| 管理员代行（豁免/替代/调整/修正/追溯） | 能力 5 |
| 角色任命与撤销 | 能力 18 |
| 考试成绩录入与修改 | 能力 10 |
| 升学审核（通过/驳回） | 能力 10 |
| 撤销学员出勤 | 能力 8 |
| 补打卡（管理员/辅导员代录） | 能力 8 |
| 特殊身份认定/变更/撤销 | 能力 12 |
| 取消虚报学员资格 | 能力 9 |
| 班级邀请码生成与撤销 | 能力 19 |
| 班级归档 | 能力 11 |
| 传承/灌顶代录 | 能力 15/17 |
| 取消共修场次 | 能力 8（DR-185）|
| 越权留级（第 3 次及以上，heldBackCount>2）| 能力 11（DR-177）|
| disqualified 再入学审批 | 能力 11（DR-156/197）|

> 共 14 类 actionType（与 08 §3.11 权威值域一致）；撤销升学（DR-184）复用「升学审核」类型 + result=revoked 标记，不另设类型。

**2. 每条日志的必填字段**：
- 操作人（`operator_id`）
- 操作时间（`operated_at`）
- 操作类型（`action_type`）
- 作用对象（`target_type` + `target_id`，如 student / class）
- 操作内容快照（变更前后的关键字段值）
- 理由（`reason`，来自操作发起时的必填字段）
- 作用域（`class_id` / `major_id`，对应能力 18 的 scope 规则）

**3. 不可删除、不可编辑**：审计日志永不物理删除，写入后不可修改（D18）。

**4. 查询权限按角色作用域过滤**：
- class_admin → 只能查本班的审计日志
- subject_admin → 只能查本学科全部班的审计日志
- super_admin → 全平台所有日志

**5. 学员可查自己相关的记录**：学员在档案中可查看与自己相关的所有审计条目（代行操作、身份变更、成绩录入等），不能查他人的。

**6. 写入方式**：审计日志是写入基础设施，各能力执行高权限操作时主动写入，不由审计日志模块主动拉取。

### 输入与输出
- 输入：各能力执行高权限操作时触发写入
- 输出：`audit_logs` 表（操作人、时间、类型、对象、内容快照、理由、作用域）

### 与其他能力的关系
- 被依赖：能力 5/8/9/10/11/12/15/17/18/19（所有涉及高权限操作的能力）
- 依赖：能力 18（查询时按 scope 过滤）

### 绝对约束
1. 日志永不物理删除、不可编辑（D18）
2. 每条日志必须记录操作人、时间、理由
3. 查询权限严格按角色作用域过滤，不允许越权查询他人班级的日志
4. 学员只能查看与自己相关的条目

### 对老项目的影响
- 老项目大概率无统一审计日志，需全新建立
- 新增 `audit_logs` 表

## 能力 21:自学模式

> ✅ **必做正式功能（DR-145，2026-06-01）**：原 ⏸ 暂缓→转必做。自学是必要功能（独立于升学体系、用户价值直接）；`UserSelfStudyProgram` 由 §五暂缓移入 §三实施，Phase 紧接 P5 后=新 P6（核心跑通即上），TODO-5 反向关联转必做。

### 业务意图
为无法加入班级跟班的师兄提供**个人自学轨道**：按个人节奏学修某科系内容、自我追踪完成量，但不参与班级中心的升学体系。自学是「自我学习」定位，不是升学路径。

### 业务规则
1. **开通限管理员**：subject_admin / super_admin 录入开通（自学是科系级操作），学员不可自助报名
2. **无班级**：自学师兄不归属任何班级，不走邀请码（区别于能力 2）
3. **进度=纯完成量**：进度按个人完成量计（完成的课时数、累计的学修量），**独立于班级**——不对标班级课表周次、无截止、无掉队判定、无休息周、无进度补足。完成多少算多少，学员自定快慢
4. **不升学**：自学不通向正科；要升学须先经邀请码加入正式班级（能力 2），届时按班级学员标准一视同仁
5. **不做共修出勤**：自学无班级、无共修，能力 8 出勤机制不适用
6. **可录个人学修数量**：念诵/观修等复用日常打卡（能力 7 / PracticeLog），纯个人追踪，不生成升学报数节点快照（能力 9）
7. **不进关怀清单**：能力 14 关怀清单是班级机制，自学无班级故不进；自学进度独立、无掉队概念故无预警
8. **状态机**：active（自学中）/ paused（暂停，学员自己切）/ completed（系统自动，全部课时完成）/ abandoned（放弃，subject_admin+）
9. **记录永久留存**（D18）：自学记录不物理删除

### 输入与输出
- 输入：管理员开通自学、学员暂停/恢复、学员录个人学修量、管理员标记放弃
- 输出：`UserSelfStudyProgram`（自学科系记录）、个人完成量进度

### 与其他能力的关系
- 依赖：能力 1（科系）、能力 5（管理员开通/管理）、能力 7（个人打卡复用）
- 区别于：能力 2（加入班级——自学不走邀请码、无班级）
- **不依赖**：能力 8/9/10/14（出勤/升学报数/升学/关怀均不适用）

### 绝对约束
1. 自学无班级，不走升学体系（要升学须先加入正式班级，能力 2）
2. 开通与放弃限 subject_admin 及以上（科系级），学员不可自助开通
3. 进度纯完成量、独立于班级，系统不判「落后」
4. 记录不物理删除（D18）

### 对老项目的影响
- 新增 `UserSelfStudyProgram` 表（08 §5.4 已设计，✅ **必做·移入 §三实施，DR-145**，随新 P6）
- Program 补 `selfStudy` 反向关联（08 TODO-5）

### 可能的呈现方式（仅供参考）
- 学员端：自学进度页（完成量、个人学修量录入）
- 管理端：subject_admin 自学师兄开通/管理页

> 本能力含三个子能力：**25.A 法义问答与功能导航（只读）** + **25.B AI 代操作（自然语言代用户查询与录入）** + **25.C 笔记 AI 文本加工（已上线现状）**（DR-107 / DR-109）。
>
> ⏸ **AI 模块整体定位（用户决策 2026-05-31，DR-109）**：AI 模块**只做后台必要部分，暂不作为正式用户功能上线**。25.A 问答 / 25.B 代操作维持暂缓（仅后台必要部分先建）；25.C 笔记加工虽已在生产环境运行，亦**不作正式能力扩展、维持现状**。

### 子能力 25.A：法义问答与功能导航（只读）

#### 业务意图
学员在法本学修中可随时向 AI 助手提问，助手基于 RAG 检索法本原文给出**有引用**的回答，或导向 App 功能入口。法义问答必须有法本原文支撑，不允许 AI 自由发挥；涉及个人修行体验/教派评判的问题导向辅导员。辅导员侧提供「班级问答洞察」，查看本班热门问题以辅助备课。

#### 业务规则

**1. 受众与权限**

| 角色 | 权限 |
|---|---|
| 学员 | 可向 AI 提问（法义问答 / 功能导航 / 修行基础） |
| class_tutor 及以上 | 只能查看本班「问答洞察」，**不可自己提问** |
| super_admin | 负责 AI 配置中心（LLM 模型、成本上限、法本索引，职能 #20 平台级配置） |

**2. RAG 法本检索范围**：覆盖**系统内全部已索引法本**，不限学员是否已加入该专业——任何学员均可问任何法本内容（DR-106）。功能导航问题全局可答。

**3. 问题分类与处理**

| 类型 | 处理 |
|---|---|
| 法义问答 | RAG 检索原文 → LLM 生成 → `[n]` 引用标注，引用可点击跳转课时 |
| 功能导航 | FeatureEntry 匹配 → 功能入口卡 |
| 修行基础（坐姿/呼吸等可标准答） | LLM 可答，范围受控 |
| 个人修行体验（梦境/感受/境界） | AI 不答，导向辅导员 |
| 教派 / 戒律 / 上师评判 | AI 不答，不参与争议 |

**4. 法义准确性是红线**：所有法义回答必须基于 RAG 检索原文并带 `[n]` 引用；检索无结果 → 直接告知"找不到明确依据，建议咨询辅导员"，不允许凭印象 hallucinate。

**5. Rate Limit**：每学员每天 ≤ 30 次提问；超限提示"今日已达上限，明天继续"，不影响功能导航。

**6. 隐私约束**：用户 PII（邮箱/姓名）不发给 LLM；学员可在 App 设置中关闭 AI 助手（关闭后入口消失）。

**7. 对话历史**：保存，学员可查看历史会话；学员可手动清空自己的历史（**物理删除**——对话历史属 UI 工具记录，非学修档案，D18 明确例外）。

**8. 成本管控**：全平台每日 LLM 成本上限（super_admin 后台配置，默认 $20/天）；超出后 AI 自动降级为仅功能导航模式。

**9. 辅导员「班级问答洞察」**：class_tutor 及以上可查看本班「热门问题 Top N」聚合统计（只展示问题文本聚合，**不展示提问学员姓名**）；用途为备课参考，不作考核依据。

#### 输入与输出
- 输入：学员提问文本、当前页面上下文（课时/法本）、辅导员查看洞察、super_admin 触发法本索引重建
- 输出：`AiConversation` / `AiMessage`（对话记录）、`ContentChunk`（法本段落向量索引）、`FeatureEntry`（功能目录）；用量统计**复用 `LlmCallLog`/`LlmProviderUsage`**（不新建 AiUsage，DR-110）

#### 与其他能力的关系
- 依赖：能力 2（确定提问者身份：学员可问 / 辅导员只读）、能力 3（法本课时被索引为 ContentChunk）、能力 18（权限：学员提问 / 辅导员洞察 / super_admin 配置，职能 #20）
- 被依赖：无（终端能力）

#### 绝对约束
1. 法义问答必须基于 RAG，绝不允许 LLM hallucinate（无依据时导向辅导员）
2. 辅导员不可向 AI 提问，只读洞察；洞察不展示提问学员姓名
3. 用户 PII 不发给 LLM
4. 对话历史允许用户物理清空（D18 明确例外：非学修档案）
5. 法本索引/成本上限等配置限 super_admin（职能 #20）

#### 对老项目的影响
- 需安装 pgvector PostgreSQL 扩展
- 新增 **4 张表**：`ContentChunk` / `FeatureEntry` / `AiConversation` / `AiMessage`（已在 08 §四 列出，⏸ 暂缓实现）；**`AiUsage` 不新建 → 复用 `LlmCallLog`/`LlmProviderUsage`**（DR-110）
- **LLM 调用层复用线上既有网关**（多 provider 调度 / 配额 / 熔断 / 每日成本上限 / super_admin 配置后台均已存在，并已在判分·出题两场景上线），仅新增 `dharma_qa`（法义问答）/ `feature_nav`（功能导航）两个场景配置；**不从零自建调用层**（DR-108，修订 DR-74 原「独立从零模块」假设）
- 技术方案详见 `docs/AI_ASSISTANT_PLAN.md`（2026-05-04 已定型）

#### 可能的呈现方式（仅供参考）
- 学员端：右下角浮动 ✨ 按钮（全局）；首页 search bar；法本/课时页内联「问问 AI」入口
- 辅导员端：班级管理页「问答洞察」Tab，Top N 热门问题
- admin：AI 配置中心 `/admin/ai`（LLM 模型、成本上限、法本索引管理）

### 子能力 25.B：AI 代操作（自然语言代用户查询与录入）

#### 业务意图
用户用自然语言向 AI 下指令——「查我加行观修还差多少座」「把今天念的 1 万金刚萨埵心咒记下来」——AI 解析意图、调用对应能力的查询/写接口；**写操作执行前必须向用户结构化确认**。把学修数据录入与进度查询降为「一句话」操作，降低操作门槛。

#### 五条铁律
1. **权限不放大**：AI 只能代用户做用户本人有权做的操作；管理员/辅导员高权限操作 AI **永不代做**
2. **只碰本人数据**：严格限于当前登录用户自己的档案
3. **写操作前强制结构化确认**：确认后才落库，可取消（含笔记在内的所有写操作一律确认）
4. **多专业必须问清归属**：跨专业不豁免（D14b），确认卡带专业选择，AI 不许擅自猜
5. **来源留痕**：代录记录标 `source=ai_assistant`（沿用能力 9 自动/手动来源维度）

#### ✅ 首批可做清单（录入类写 + 全部查询）

| 类别 | 范围 |
|---|---|
| 写（录入类） | 日常打卡（能力 7）、内加行计数含法王祈祷文（能力 6）、加行观修录入（能力 4）、约修贡献打卡（能力 24）、笔记 |
| 查（全部只读） | 闻思进度（3）、观修进度（4）、内加行累计（6）、日常打卡（7）、共修出勤（8）、报数快照（9）、升学资格进度（10）、传承/灌顶（15/17） |

#### ❌ AI 禁区清单
- 一切管理员/辅导员高权限操作：代行豁免（5）、升学审核/成绩录入（10）、角色任命（18）、撤销出勤/取消资格（8/9）、邀请码（19）、班级归档（11）
- 状态变更类（首批不开放）：退出专业（11）、设主修、改隐私/关 AI 设置
- 报数节点快照触发（能力 9 由系统自动生成，AI 不代触发）
- 替任何他人操作

#### 确认机制
- 写操作 → AI 生成结构化确认卡（操作类型 / 项目 / 数量 / 归属专业 / 时间）→ 用户确认 / 取消 / 修改
- 意图解析不确定（数量、项目、专业识别不清）→ **不执行，向用户澄清追问**
- 绝不静默写库

#### 纠错路径（沿用能力 9）
- 确认环节是主防线
- 落库后发现错 → 学员不能自改（能力 9 规则 5）→ 联系管理员走能力 5「修正记录」代行，留痕（D17）
- 记录带 `source=ai_assistant`，便于管理员核查

#### 留痕定位
- AI 代操作 = 用户授权 AI 代为录入，本质是用户本人操作（**非** D17 管理员代行豁免）→ 不进 AuditLog（能力 20 只记高权限操作）
- 记录带来源标记；AiMessage 记录本次工具调用与结果，关联产生的记录 id，可追溯

#### 数据契约影响（提前设计产出）
- **不新建业务表**，复用各能力既有写路径
- 各写表（PracticeLog 等）来源标注扩展支持 `ai_assistant` 值
- AiMessage 扩展 `toolCall` / `actionResult`（关联记录 id）字段
- 仍 ⏸ 暂缓实现（随 AI 模块），字段契约现在定稿，避免上线后给写路径返工（08 §十 TODO-AI-2）

#### 绝对约束
1. 权限不放大、只碰本人数据
2. 写操作无确认不落库
3. 高权限操作 AI 永不代做
4. 多专业归属必须显式确认（D14b）
5. 落库后纠错走能力 5，不给自助改（与能力 9 一致）

### 子能力 25.C：笔记 AI 文本加工（已上线现状 · DR-109）

> ⏸ **已上线但不作正式能力扩展**（DR-109）：本子能力为如实登记线上既有功能（避免 source-of-truth 留孤儿、满足「每功能必有标签」铁律），受本能力顶部「AI 模块整体暂不上线」定调约束——维持现状运行，不扩展、不作正式功能推进。

#### 业务意图
学员对**自己写的笔记**用 AI 做纯文本加工（润色措辞、生成摘要等），降低记录门槛。**不涉及法义解释**——与 25.A 红线方向相反（25.A 必须基于法义，本能力严禁碰法义）。

#### 业务规则
1. **5 个 action**：润色（polish）/ 摘要（summarize）/ 打标签（tags）/ 拟标题（title）/ 起草草稿（draft，可用本课全文生成）
2. **严约束红线**（沿用线上现状）：不解释法义 · 不评价宗教内容 · 不发挥 · 不引申 · 仅按指令处理用户文本
3. **仅本人笔记**：作用对象限学员自己的 Note（沿用 25.B 铁律 2「只碰本人数据」）
4. **输出是建议**：AI 返回文本，采不采纳由学员决定，不自动落库改写
5. **复用既有 LLM 网关**（DR-108）：调用走 gateway，无独立调用层

#### 表
- **零新表**：复用既有 `Note` 表；无状态调用，不需要对话历史表（AiConversation/AiMessage 不为本能力新增）

#### 与其他能力的关系
- 依赖：能力 2（识别本人身份）；复用 25.B 铁律 2（只碰本人数据）
- 与 25.A 红线相反：25.A 必须基于法义、本能力严禁碰法义，故独立子能力不并入 25.A

#### 现状（线上已运行）
- 后端：`POST /api/notes/llm-assist`（`notes/llm-assist.service.ts`，5 action，调用 gateway）
- 前端：NotesDrawer「📑 用本课全文生成 AI 草稿」等入口
- 受 DR-109 约束维持现状，不扩展

## 能力 26：综合修学积分排行

### 业务意图
班级内学员的综合修学排行榜，按多维度学修量加权计分，激励学员。学员可在班级页查看周/月/全部三个周期、综合/念诵/观修三个维度的排名。

### 业务规则
1. **三周期**：week / month / all（5 分钟 in-memory 缓存，与观修排行同套路）
2. **三维度 tab**：综合（积分制，默认）/ 念诵 / 观修
3. **综合积分公式**（v1 写死，**v2 admin 可配权重**）：
   `积分 = 念诵遍数×0.01 + 观修完成数×5 + 观修时长(分)×0.1 + 答题数×0.5 + 阅读课时×W_READING + 活跃天数×W_ACTIVE_DAY`
4. **范围限本班主修法本**：各维度仅统计本班法本范围内的学修量（审计 S4）
5. **隐私尊重**：修学维度（念诵/答题/阅读/活跃天数）受 `practiceVisibleToClass` 管；观修维度受 `meditationVisibleToClass` 管；关闭可见性的成员不进榜（与能力 7/4 隐私开关一致）

### 输入与输出
- 输入：classId + period
- 输出：排序后的 StudyRankingRow[]（含 score + 各维度原始数：chanting/meditationCount/meditationMin/answerCount/readingLessons/activeDays）

### 与其他能力的关系
- 依赖：能力 4（观修）/ 6/7（念诵打卡）/ 3（答题、阅读）的学修数据
- 关联：班级观修排行（DR-122 实时算）是本能力「观修 tab」的子集

### 绝对约束
1. 仅班级成员可见（非公开）
2. 各维度独立尊重对应隐私开关
3. v2 权重可配时，配置项归 super_admin（职能 #20 平台级配置）

### 对老项目的影响
- ✅ 线上已实现（`ClassRankingPage` + `practice/study-ranking.routes.ts`），积分公式已写死运行
- 改造方向：v2 权重数据化为专业/平台配置项（D3）
- ⚠️ **数据源改造关联（TODO-23）**：积分公式的**念诵维度 + 活跃天数维度**读 `PracticeDailySummary`——该表实修域改造后**已废弃**（DR-122），改造时须改为**实时聚合 PracticeLog**（与观修排行实时算同口径）；观修/答题/阅读维度（MeditationSession/UserAnswer/LessonReadingProgress）不受影响

### 业务意图

## 能力 45：短信通道（SMS）🆕 新建

> 🆕 线上无·实为新建（DR-126，D 组 D3，DR-132；TODO-SMS 已决策 DR-139）。**线上零实现**：User 无手机号字段、无短信服务商、dispatch 仅占位注释。用途：重要通知兜底 + 关键学修提醒（用户决策）。**DR-139 拍板：独立 SmsLog 表（§三 18→19）+ 后台场景级开关 + 服务商不锁定 + 验证码标准档。**

### 业务规则

**A. 前置：手机号体系（🆕 缺口）**
1. **User 加手机号字段**（🆕）：`phone String?`（国际格式）+ `phoneVerified Boolean` + 可选 `phoneVerifiedAt`

**B. 短信发送抽象层（🆕）**

**C. 作为 dispatch 第 3 通道**
6. **channel='sms'**：dispatchToUsers 接入 sms 通道——派发去重仍走 DispatchLog（channel='sms' 跨通道统一账），**短信发送明细 + 短信级幂等走独立 SmsLog**（DR-139 分工）

8. **降级链**：站内信（必达）→ Web Push（有订阅则推）→ SMS（critical/关键 且符合用途规则）

**D. 短信用途规则（用户决策：兜底 + 关键学修提醒）**

- **三端处理**：admin 处理两类；辅导员处理本班笔记举报（三端分离）

## 能力 51：用户反馈（bug/建议）

> ✅ 线上已实现·纳入设计（DR-126，C 组补充；接 DR-118/119 Feedback 净资产，DR-138）。grep 验证：Feedback 表真实存在。**用户提交 bug/建议/其他 → admin 处理回复的反馈闭环。统一一张 Feedback 表，kind 区分类型（用户决策：拆为独立能力）。**

### 业务意图
用户（含匿名/未登录）提交产品问题反馈、bug 报告、功能建议，admin 处理并可回复，支撑产品迭代与问题修复。

### 业务规则

**A. 提交（统一一张 Feedback 表）**
1. **类型区分**（kind，FeedbackKind 枚举）：bug / 建议 / 其他——**bug 反馈与问题反馈同一张表，kind 区分**（无需为 bug 单独建表）
2. **提交**（`POST /api/feedback`）：message（内容，service 层限长）；支持**匿名提交**（userId 可空，匿名可留 contactEmail）
3. **复现信息**（自动采集）：page（哪个页面）/ userAgent / appVersion（前端 build）/ sessionId（关联 analytics/sentry）——便于 bug 复现
4. **状态**：FeedbackStatus 默认 open

**B. 处理（admin）**
5. **待处理列表**（`/api/admin/feedback`）：按 status + createdAt
6. **处理**（`/api/admin/feedback/:id`）：记 handledByUserId/handledAt + response（admin 回复，可选）

**C. 我的反馈**
7. **查看**（`/api/me/feedback`）：用户查自己提交的反馈及回复
8. **入口**：HelpPage（帮助页）

### 输入与输出
- 输入：用户提交（kind + message + 可选 contactEmail）+ 自动复现信息 + admin 处理回复
- 输出：反馈记录 + 处理状态 + admin 回复

### 与其他能力的关系
- **区别能力 50 举报闭环**：反馈=产品 bug/建议（面向产品团队），举报=内容合规审核（题目/笔记下架）；两者业务面不同，独立登记
- **关联能力 28**：sessionId 关联会话/分析
- 联动通知：admin 回复可通知反馈者（能力 43，⚠️ 是否推送待定）

### 绝对约束
1. 支持匿名提交（userId 可空，匿名留 contactEmail 才能收到回复）
2. 自动采集复现信息（page/userAgent/appVersion/sessionId）——便于 bug 定位
3. message 长度限制（service 层）
4. bug/建议/其他统一一张表，kind 区分（不为各类型单独建表）

### 对老项目的影响
- ✅ 线上已实现（`HelpPage` + `feedback/` 模块 + Feedback 净资产 + admin 处理）
- 接 DR-118/119（Feedback 由弱②提为明确保留净资产），本能力正式登记为业务能力
- 复用净资产，无新表
