## 一、WP-A · app 需求符合性（最关键发现）

### 核心发现：当前 SoT 设计只到「业务层 + 数据层」，**API 层与页面层缺位**

| 设计层 | 权威档落点 | 状态 |
|---|---|---|
| 战略层 | 05-decision-log（D1-D20） | ✅ 完整 |
| 权限层 | 02-roles-and-permissions（23 职能） | ✅ 定稿 |
| **业务层** | 06-business-capabilities（能力 1-25） | ✅ 定稿 |
| **数据层** | 08-merged-design（表/字段/Migration/Phase） | ✅ 进行中·近完整 |
| **API 契约层** | —— | ❌ **权威档未产出** |
| **页面/交互层** | —— | ❌ **权威档未产出**（仅 06 各能力「可能的呈现方式」标"仅供参考"） |

**API/页面 设计当前只存在于两处，都不是目标态权威档**：
- `FINAL_DESIGN_SANSUSHENG.md`（§三 28 API 模块 / §四 页面）——**旧设计**，07-integration-plan 第11-12行明确"只读不改、仅参考字段命名与 API 模块划分"，且**早于 08 的 98 轮改动**，与当前表设计已脱节。
- `audit/05-api-endpoints.md`（139 端点 / 26 模块）——**线上现状快照**，是"现在有什么"，非"目标应该是什么"。

### 影响
- **"app 是否满足需求"在交互层面无法从权威档验证**：三端用户旅程的"页面闭环"、API 契约的输入输出，SoT 里没有目标态设计可对照。
- 子 agent 报的页面断点（邀请码输入页、学期报数 UI、留级转班 UI、关怀掉队页、出题 UI…）是**针对旧档 FINAL_DESIGN 的覆盖率（~60%）**，参考价值有限——真问题不是"旧档缺哪页"，而是**目标态 API/页面层尚未在 SoT 产出**。

### 判定与建议
- ⚠️ 这是**设计深度的边界**，可能是有意（API/UI 留给实施阶段），也可能是遗漏。
- **需你决策**：要不要在权威档补一层「API 契约 + 页面/交互」设计（类似 06/08 的严谨度），让 app 需求可在 SoT 层面验证闭环？还是明确"以现状 audit/05 + 旧档 FINAL_DESIGN 为实施参考基线"，SoT 只维护到数据层？
