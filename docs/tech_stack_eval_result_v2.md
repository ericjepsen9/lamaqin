## 0 · 摘要（TL;DR）+ 我的诚实判断

**一句话结论（带取舍）**：证据指向 **「sss 原栈（Supabase + Expo/RN），把觉学当『参考实现』而非继承代码」** 是构建本设计效率最高的路径；「继承觉学整套代码改业务」在「60k 行已建」的表象下**实际省力远小于直觉**，且要付出三笔隐藏成本（弃 sss 已建库 / 非原生 / realign 税）。但若 PM 高度看重觉学**学习引擎 + 基础设施 + LLM 网关**这半套成熟资产、且能接受 Web/Capacitor 形态，觉学栈仍是**正当的次选**。

**⚠️ 先纠一个框架偏差（铁律：想法有问题直接指出）**：
简报把张力描述为大致对称的二选一——「继承觉学已建代码 vs sss 干净补 App 代码」。**实测后这个天平并不对称**，原因有三（详见 §3.2 / §4）：

1. **觉学已建的，多是 sss 要砍/延后的那半。** 觉学线上做得深的是「学得好不好」（题库/SM-2/错题/收藏/笔记/高亮/阅读器/积分/成就/AI 判分/AI 出题/藏历/画报/通知）。但 sss v2.0 **砍掉**积分排行/成就徽章/成就通知/AI 判分/AI 出题/社交 feed/灌顶/内容举报/A-B 实验，**延后**错题本/收藏/笔记高亮/阅读器/约修（决策 103/108/111/112/115/116/117）。→ 这部分「复用」相当一部分是**隐藏或关掉，而非省工**。
2. **sss 真正要的核心，在觉学也基本没建。** 佛学院学修管理主体——专业体系/升学判定/共修出勤/学期报数/传承/4 角色/考试——觉学线上**几乎空白**（🆕，约 **40+ 张表要从零建**，DR-130 已钉死「08 文档『新建 20 张』严重低估」）。→ 觉学对「最难的那块」几乎没有头部优势。
3. **继承觉学 = 同时弃掉 sss 已建的生产库 + 放弃原生。** sss 的 Supabase 生产库（51 表 + 131 条 RLS + 进度算法实测 10/10）**本身就是最新设计的源**（最干净的对齐），且 PM 已 bless「sss=最终生产库、不重建」。觉学栈是 Fastify/Prisma 应用层鉴权，与 RLS 中心化是**相反范式**，继承它等于弃用这套已建资产；且觉学前端是 React Web（Capacitor 套壳），**不是 React Native**，与 sss 锁定的原生体验（决策 #170）冲突。

**三个候选（详见 §4-§6）**：
- **方案 A（主推）**：sss 原栈（Supabase + Expo/RN），觉学作参考实现（抄设计、抄算法逻辑，不抄代码库）。
- **方案 B（对照/次选）**：继承觉学栈（Fastify/Prisma/React+Capacitor），按最新设计 realign。
- **方案 C（折中变体）**：Supabase 数据/鉴权/RLS 留作底座，前端评估复用觉学 React 资产（Capacitor）或仅搬逻辑。

## 2 · 需求侧：最新设计对技术栈到底提了什么要求

从决策 001-130 提取**影响选型**的需求（不是全功能清单）。关键发现：**本设计的技术形态相当"轻后端"**——无强实时、v1.0 无离线、核心难度在「海量数据驱动后台配置 + 管理端十一」而非高并发/低延迟。

| 维度 | 需求实况 | 对选型的含义 |
|---|---|---|
| **实时性** | 几乎无 websocket 需求；审批 status、共修场次、在修人数都是**轮询/聚合查询**（决策 058/065/102）| 两栈都轻松满足；Supabase Realtime 非必需 |
| **离线/乐观 UI** | v1.0 **不做**乐观 UI、不做离线同步（决策 089）；唯一离线=音频下载（文件级，决策 080）| 不需要 local-first 同步引擎，**消解了"原生离线难"的顾虑** |
| **推送/定时** | ⚠️ **"克制不推送"红线已被决策 062 推翻**——App 会推送（含催促类 C）。四类推送框架（决策 068）+ **系统推送走 Edge Function 定时/事件触发**（当日未打卡/断签3·7天/共修前30分/法会开始/每周回向）| **需要服务端定时（cron）= Edge Function**；客户端 expo-notifications（A 已在锁定栈） |
| **AI/LLM/RAG** | **AI 判分/出题永久砍**（决策 108）；反向补**法义问答**，但 **v1.0 仅 RAG 检索**（返原文+引用，零 hallucination），生成式 LLM 后引入（决策 109）；颂词题=**本地判分**非 AI（105/106）| v1.0 只需**检索基建**（向量/全文，pgvector）+ Edge 网关；**生成式 LLM 网关 v1.0 不急** |
| **文件/媒体** | 音频→**Supabase Storage**（在线+下载离线）；视频→**YouTube**（react-native-youtube-iframe）；媒体 URL 走 DB 字段（预留迁 R2）；无证书生成需求（待核）（决策 080）| 锁定栈已覆盖 |
| **认证/角色/RLS** | 邮箱 OTP（Supabase Auth）；**审批门** pending→active（DB 触发器，决策 058）；入班全 admin 分配（126/127）；**扁平 4 角色 + 数据范围**（决策 103）；重度 RLS 贯穿；**#193 具名互看=永久红线** | RLS 中心化模型与 Supabase 天然契合；觉学 4 管理角色与 sss **非 1:1**，需重映射 |
| **后台数据驱动配置（最大工作量源）** | 极多：愿模板/限时标记/代替方案/限时年限/必需传承清单/考试合格线/7 题型/休息周/可选经典/留级次数/Excel 排表导入…+ **管理端 M1-M15 全套**（决策 120/122/124/125/128/129/130）| **两栈都要写这一大坨**；这是真正的工作量大头，**与选哪个栈关系不大**——更取决于"管理端 UI 在哪套前端写得快" |
| **时区/进度算法** | 四层时区（存储 UTC / 班级 IANA / 藏历 UTC+8 / 个人手机本地）；**进度算法在 DB**（RPC，(学期号,学期内周)，实测 10/10，决策 091/072）| date-fns-tz 已锁定；**算法已在 sss DB 落地并测过**——换栈=重写或保留为裸 SQL |
| **外部集成** | 邮箱 OTP（Supabase Auth）；**短信 critical 级**（决策 116，外部 SMS + Edge）；YouTube；无支付；WhatsApp=纯文本复制非 API | 外部集成都走 Edge Function（碰密钥/外部）|
| **明确要服务端逻辑** | 注销删 auth.users（Apple 硬要求，Edge，决策 078）、系统推送触发（Edge cron）、短信（Edge）、RAG 网关（Edge）；DB 层=进度算法/学号生成/审批建档/主班事务函数 | **明确"不建独立服务器（NestJS）、服务端逻辑用 Edge"**（CLAUDE.md §6.5，决策反复确认）|

> **选型层面的关键启示**：① 本设计**不靠强后端能力取胜**（无实时、v1.0 无离线、无高并发）——这削弱了"觉学有成熟 Fastify 后端"的相对价值；② 工作量大头是**管理端十一 + 数据驱动配置 UI**，**两栈都得从头写**（觉学这部分也没有）；③ 真正已沉淀的差异资产是：sss 侧=**已建并对齐的 DB+RLS+算法**，觉学侧=**学习引擎 + 通知/账户基建 + LLM 网关**。

## 3 · 两套候选的现状事实

### 3.1 sss 原栈现状

- **栈**（CLAUDE.md §1 已锁定，约 13 核心依赖）：Expo SDK53+ RN + TS / Expo Router / NativeWind v4 / RN Reusables / Zustand / TanStack Query v5 / RHF+Zod / date-fns(-tz) / Lucide RN / **Supabase**（PostgreSQL + Auth + RLS + Storage + Realtime）+ expo-notifications。决策准绳：Claude Code 顺手 > 版本绑定、代码所有权、稳定 > 性能、TS 友好（tech_stack.md #161-169）。
- **DB/后端：已建且已对齐**。Supabase 生产库 `sss` 全量 schema v2 + RLS 已建（2026-06-01，PM bless「最终生产库、不重建」）。规模：**约 51 表 / ~22 函数（含进度算法三函数 + SECURITY DEFINER RPC）/ 131 条 RLS 策略（84 处 auth.uid()）/ 19 触发器 / 2 聚合视图**；text+CHECK 代替原生 enum。**进度算法实测 10/10**。**这套 DB 本身就是最新设计的事实源 = 最干净的对齐。**
- **App 端：本库为 0**。本仓库当前只有 `docs/`（18 个文档）+ CLAUDE.md，**无 app 代码、无 components/lib、无 `supabase/migrations/`**（迁移真源在别处）。即 **Expo/RN 前端 + lib/queries + Edge Functions 100% 待写**。
- **架构特性**：重度绑定 Supabase（RLS、auth.uid()、SECURITY DEFINER、触发器维护不变量）——**留在 Supabase=资产；迁出=整套授权层 + auth.users 耦合 + 触发器不变量都要重写**（这正是不该选 B 去搬库的技术原因之一）。

### 3.2 觉学栈现状

- **栈**：前端 React 18.3 + Vite 5.4 + TS + TanStack Query + Zustand + React Router DOM 7 + **Capacitor 8.x**（iOS/Android 套壳）+ Web Push/VAPID；后端 **Fastify 5.2 + Prisma 6.1 + PostgreSQL 16 + Zod + @fastify/jwt + Sentry**；**自建 LLM 网关**（minimax/claude/deepseek 多 provider + 熔断/配额/成本/场景路由，已上线 AI 判分 + AI 出题场景）；asia-relay（法本抓取中转，绕大陆 YouTube）。2 台 OCI 生产服务器，PM2 部署。
- **数据/接口规模**：**60 model / 19 enum**、**139 端点 / 26 模块**（REST）。
- **现网=旧的轻量"学习 App"**：仍是**三元单值角色 enum（admin/coach/student）**，新 4 角色（UserRoleAssignment）**未实现**。
- **能力分布（最关键）**：
  - **已建（净资产，多在能力 26-51）**：题库答题/SM-2/错题本/收藏/笔记高亮/法本阅读器/藏历/画报/系统公告/通知 v2/账户安全/审计/分析/A-B/反馈/积分/成就/AI 判分网关——**学习引擎 + 运营 + 账户 + 通知 + AI 网关这半套成熟**。
  - **基本空白（能力 1-25 学修管理核心）**：覆盖度 `✅~2 / 🔧~11 改造 / 🆕~11 从零 / ⏸5 / ❌1`（`03 §2`）。专业体系/升学/出勤/报数/传承/4 角色/考试**线上几乎没有**，**约 40+ 张表要从零建**（DR-130：08「新建 20」严重低估）。
- **复用正面信号**（`audit/02`）：后端鉴权架构干净（单一入口 auth.ts + requireRole 工厂 + 班级断言，改造有收口点）；前端三端分离 ~85-90%（学员/coach/admin 路由+守卫齐）；基础设施成熟（邮箱验证/密码重置/单设备登录/通知 v2 多通道去重/LLM 网关/埋点/错误日志/孤儿文件回收）；AI 不从零（既有网关加 dharma_qa/feature_nav 两场景即可，DR-108/110）。
- **realign 成本信号**（负面）：角色模型是主战场（**44 处 requireRole + ~16 admin bypass + 17 班级断言 + ~15 硬编码角色判断**，且 **JWT 结构必改→已签发 token 全失效需全员重登**）；**实修打卡是结构性重构**（纯计数器 → vow/时长制，非加列，DR-121/122）；**专业×届归属需逐班人工补**（线上 Class 直绑单 courseId，无专业×届维度，无法纯自动）；enrollment 迁 LessonCompletion；**Prisma 迁移仅 2 个（db push 历史），无大规模迁移脚本先例**；**无代码测试**。
- **待核**：实际 LOC、测试覆盖率、是否有"必须迁移"的真实生产用户数据（注：觉学生产数据是觉学自己的用户，sss 有自己的 91 师兄 + 自己的库——继承代码 ≠ 继承数据，但要核清）；pgvector 线上尚无（RAG 需补）。

## 4 · 三个候选方案（含取舍）

### 方案 A（主推）· sss 原栈（Supabase + Expo/RN），觉学作"参考实现"
- **做法**：在已建且已对齐的 Supabase 库上，按最新设计**直接写 Expo/RN App + lib/queries + Edge Functions**。觉学不作为代码库继承，而作为**参考实现**：抄它的设计取舍、抄可移植的**算法逻辑**（题型本地判分、SM-2 调度、RAG/LLM 网关设计模式、通知去重/频率思路），用 RN/Edge 重写；UI 直接用已共享的觉学视觉 tokens（JUEXUE_TOKENS.md，sss 早已提取）。
- **取舍**：✅ 最干净对齐（DB 即设计源）/ 充分利用已建 DB 资产 / 符合 §1 锁定栈 / 真原生（App Store + expo 原生推送）/ Claude Code 顺手（训练数据最多、greenfield 照规格写）/ PM 最易逐功能验证。❌ App 全量新写；学习引擎 + LLM 网关要"参考着重写"（非现成搬入）——靠觉学当参考来降风险/提速。

### 方案 B（对照/次选）· 继承觉学栈（Fastify/Prisma/React+Capacitor）+ realign
- **做法**：fork 觉学代码库，保留学习引擎/基建/LLM 网关/三端前端骨架，按最新设计砍/改/补，建那 40+ 张核心表，重做角色模型。
- **取舍**：✅ 学习引擎 + 通知/账户基建 + LLM 网关这半套**真复用**（对存活的净资产能力省工）；AI RAG 近乎免费（成熟网关加 2 场景）；后端鉴权有干净收口点。❌ **弃用已建 sss DB+RLS+算法**（与 PM「不重建」bless 冲突）/ 学修管理核心 40+ 表**仍要从零建**（觉学也没有）/ realign 税不小（角色 44+ 触点 + JWT 全失效 + 打卡重构 + 专业×届人工补）/ **非真原生**（React Web + Capacitor，碰 #170 红线与体验）/ **推翻 §1 锁定栈**/ 继承的是**无代码测试**的 60k 行外部代码（非程序员 PM + Claude Code 在大型他人代码上做"外科手术式"改造，风险与认知负担高于 greenfield）/ 进度算法（实测 10/10）要重写或降级为裸 SQL。

### 方案 C（折中变体）· Supabase 留底座 + 评估复用觉学前端
- **做法两味**：
  - **C1（≈A 的强化）**：留 Supabase 全套，前端用 Expo，但**搬觉学的逻辑代码**（判分/SM-2/网关/通知逻辑）。≈ 方案 A 的"参考实现"做法，**推荐并入 A**。
  - **C2（保前端代码）**：留 Supabase 数据/鉴权/RLS，**复用觉学 React 前端**（~40 学员 + ~21 admin 页）+ Capacitor 套壳，把前端的 API 调用从觉学 Fastify **改接 supabase-js**。
- **取舍（针对 C2）**：✅ 既留已建 DB、又复用最多前端 UI 代码。❌ 要**拆掉觉学的 Fastify API 层（139 端点）改接 supabase-js**——这层 rewiring 不小，"复用"打折；且仍是 Web/Capacitor 非原生；两套范式缝合，可维护性偏低。**C2 的净省力存疑**，列为变体备选。

## 5 · 对比矩阵（按"效率"维度）

## 6 · 推荐（2-3 个，带理由，诚实不预设）

### 🥇 主推：方案 A（sss 原栈 + 觉学作参考实现）
**理由**：
1. **对齐最干净、返工最少**：已建 Supabase 库本身就是最新设计的事实源；照规格写 App，不背 realign 包袱（B 的 realign 是在"砍/改/补"三种动作里穿针引线，易错且难验）。
2. **充分利用既有资产、不与 PM 既定 bless 冲突**：DB+RLS+进度算法（10/10）直接用；不浪费已建生产库。
3. **符合 §1 全部准绳 + 红线**：Claude Code 最顺手、代码所有权、稳定、TS 友好、真原生、"服务端逻辑走 Edge"。
4. **本设计是轻后端形态**（无实时/v1.0 无离线/无高并发）——觉学"成熟 Fastify 后端"的相对价值被削弱；真正的大头（管理端十一 + 数据驱动配置）两栈都得从头写，写在 Expo 一套响应式代码里（师兄端+管理端同 App，决策 #171）更省。
5. **用觉学降风险**：把觉学当参考实现，抄设计/抄算法逻辑/用已共享视觉 tokens，**把"从零写学习引擎+RAG"的风险压下来**——既得对齐与所有权，又不真背 60k 行继承债。

**主推的诚实代价**：学习引擎（题库/SM-2/复习）、通知派发逻辑、RAG 网关要"参考着重写"，不是现成搬入；上线时间取决于 App + Edge 的开发节奏。

### 🥈 对照/次选：方案 B（继承觉学栈 realign）
**它在什么条件下才更优**（请 PM 对照自己的权重）：
- 你**高度看重**觉学学习引擎 + 通知/账户基建 + LLM 网关这半套成熟资产，且**能接受 Web/Capacitor 形态**（放宽决策 #170 的真原生诉求）；
- 且**愿意弃用已建 Supabase 库**（推翻"不重建"bless）、接受角色/JWT/打卡重构的 realign 税；
- 且团队（PM+Claude Code）对在**无代码测试的大型继承库**上做改造有信心（强烈建议先挂上觉学 repo 做真实代码体检再定）。
- 满足这些，B 对"存活的净资产能力 + AI RAG"确有省力；否则其表象省力会被三笔隐藏成本吃掉。

### 🥉 折中变体：方案 C
- **C1（搬逻辑不搬库）= 并入主推 A 执行**，是把"觉学作参考"落到实处的具体手法，**建议直接采纳为 A 的一部分**。
- **C2（留 Supabase + 复用觉学 React 前端 + Capacitor）** 仅在"PM 想最大化复用前端 UI 代码、又不肯弃 Supabase、且接受非原生"时考虑；但前端改接 supabase-js 的 rewiring 会抵消部分省力，**净收益存疑，列为备选**。

> **我的诚实倾向**（非 yes-man）：**A（含 C1 手法）**。不是因为"sss 是自家栈"，而是证据显示——觉学已建的省力集中在 sss 要削减的那半、核心难点两栈都得重写、继承还要赔上已建库与原生体验。若 PM 的权重明显偏向"成熟学习引擎/基建/AI 网关的即取即用 + 可接受 Web 形态"，再认真上 B（并先做代码体检）。**最终请 PM 拍板**。

## 7 · 风险 + 迁移/改造成本（分方案）

**方案 A 风险**：
- 学习引擎/RAG 从参考重写，若觉学参考吃得不透→重复踩坑（缓解：挂觉学 repo 抄具体实现；或先做净资产能力的小切片验证）。

- App 工作量大头（管理端十一 + 数据驱动配置 UI）是硬工作量，**与选栈无关**，需如实排期。

**方案 B 风险/迁移成本**：
- **弃用 sss 已建库**（沉没成本）或痛苦移植；与 PM「不重建」bless 冲突。
- realign 触点广：角色 44+ 处 + JWT 全失效重登 + 打卡结构性重构 + 专业×届逐班人工补 + enrollment 迁移；在**无代码测试**基线上做，回归风险高。

**方案 C2 风险**：前端 rewiring（拆 Fastify API 接 supabase-js）工作量 + 双范式可维护性 + 非原生；净省力存疑。

### 10.1 体检推翻 / 确认 / 需纠偏

### 10.3 重判结论

**倾向不变、理由更新、差距收窄：仍主推 A——但升级为「A + 定向收割觉学基建」**。审计恰好把"哪些是低耦合、可干净抽取的高价值件"列清了，让收割可落地：
- **可定向抽取到 sss/Edge 的高价值件**：LLM 网关（整体最高价值、最低耦合，生成式 LLM v1.5+ 时抽，可独立 package/小 sidecar）、**SM-2 `algorithm.ts`（纯算法直接搬）**、答题**评分策略（纯判分逻辑可提取）**、scheduler/通知派发逻辑（作 sss Edge cron 推送参考）、tsvector 全文检索（作 v1.0 RAG 检索起点）、测试/CI 模式 + 视觉 tokens。
- 这样能拿到 **B 的大部分真实价值（基建 + 网关 + 测试模式）**，却不付 B 的代价（**保持真原生、保留已对齐的 Supabase RLS DB、守 §1 锁定栈、安全仍在 DB 层**）。

**但必须诚实承认 B 现在更有竞争力**：测试/CI 完整 + 基建工程质量高，把 fork-改造风险显著降下来。**B 是正当选择**——如果 PM：(a) 接受 **Web 形态（放弃真原生 #170）**、(b) 接受**弃用已建 RLS DB、安全降到应用层跨 60 模型重写隐私红线**、(c) 看重"~3-4 周基建头部 + 单一 Fastify/Prisma 代码库 + 现成测试/CI"。

**一句话**：代码体检把 B 从"看着省其实坑多"修正为"基建确实省 3-4 周、工程质量好——但省的是**基建**不是**产品大头**，且要拿**真原生 + 已对齐 RLS DB**来换"。在 91 师兄规模、隐私红线重、要原生、工作量大头是域+管理端 UI（两栈都从头）的现实下，**A + 收割**仍是效率最优；**纯 fork（B）** 适合"可接受 Web + 愿弃 RLS DB"的取舍偏好。

### 10.4 重判后给 PM 的两个真正决断点
1. **真原生 vs Web**：觉学既不提供原生（纯 Web、Capacitor 未落地），是否仍坚持决策 #170 的真原生？坚持→A+收割；可接受 Web→B 才进入强竞争。
