# 测试计划·技术功能(A线) + 业务语义(B线)两线并行(2026-07-13)

> 来源:PM 2026-07-13 提出"自建功课目标数量可填0"这个真实bug后,讨论出的系统性排查计划。
> 起因判例:师兄端"自建功课"目标数量输入框当前无最小值校验,填0能成功提交——这是**技术功能类**问题的一个具体样本;
> 讨论中PM进一步追问"操作流程和结果是否符合设计文档/教学大纲",由此拆出**业务语义类**这条独立的线。
> 两线性质不同、方法不同,故分开列、分开排期,但都要做,互不替代。

---

## 0 · 两线区别(先说清楚为什么要分两条,不是一条测试计划的两个章节)

| | A线·技术功能正确性 | B线·业务语义正确性 |
|---|---|---|
| 回答的问题 | "代码做的事,是不是代码本来该做的事"(校验/权限/并发/状态机等编程层面对不对) | "代码算出来的结果,是不是大纲/设计文档要求的那个结果"(阈值/规则/口径本身对不对) |
| 能否用自动化断言/模拟点击验证 | ✅ 能,而且可以直接写——"该拒绝无效输入"这类正确答案不需要额外调研,写完断言就能跑 | ✅ **同样能**(这次会话`tests/casebook/`配套的SQL断言,比如HQ-8盲聋听2遍判例,本质就是B线的自动化验证)——**但断言里的"正确答案"没法凭空写**,必须先做一步自动化替代不了的工作:去读大纲原文/`design_v2_decisions.md`把具体规则/数字提炼出来,并核实提炼本身没引用错误(独立审计)。这一步做完,后面写断言(SQL/jest/Playwright模拟点击均可,看规则在哪层暴露)跟A线是同一类技术活。 |
| 方法 | 摸底盘点 → 判例定规则 → **自动化断言/模拟点击**批量试错误值 → 修复 | 摸底盘点 → **先做文档审计提炼"正确答案"**(不可省、不可自动化的一步)→ 独立审计复核提炼是否准确 → 写自动化断言验证系统实际行为与提炼结果是否一致 → 修正引用/实现 |
| 本次会话已有先例 | 这次讨论前发现的"目标数量填0"| 出勤85/70阈值查无大纲依据、决策017引用错误、盲聋"听/看2遍"判定曾偏松、e2e时区计算bug 等——**均是B线性质,且都是"顺手"发现,不是专门排查出来的**,说明未发现的同类问题大概率还有 |
| 优先级判断 | 出错代价通常可恢复(admin能手动改正数据) | 出错代价可能直接影响学员真实学籍/考核结果,发现得越晚代价越高 |

**结论:两线都要做,B线不比A线次要,建议同等优先级排期,不是"测完A线再测B线"。**

## B线·业务语义正确性审计

### B线方法论
分两步,第一步不能自动化、第二步可以(包括模拟点击):
1. **文档审计提炼**——先把每条规则的"正确答案"从大纲原文/`design_v2_decisions.md`/`requirements_master`里找出来、引用到具体行号,仿照这次会话反复用过的"记录决策+一致性检查"模式,做**独立审计**(不采信自己最初的比对结论,另开一次核查)确认提炼本身没有引用错误。这一步是文档阅读+比对,没法靠点击/跑脚本代替。
2. **写自动化断言验证**——提炼出"正确答案"之后,把它写成断言去验证系统实际行为是否一致——可以是SQL/jest(这次会话`tests/casebook/`配套的判例断言就是这类,比如HQ-8盲聋听2遍判例),也可以是Playwright模拟点击UI(如果这条规则的表现在前端交互层)。这一步跟A线技术上是同一类工作,只是"正确答案"来自第1步而不是通用软件工程常识。
