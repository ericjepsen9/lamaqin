## DEF-1 · 状态枚举去留：`slightly_behind` / `will_overdue` 两态删不删 + `will_overdue` 与"截止日临近"推送的关系

**规格现状（带出处）**
- 权威阈值只列 **3 态**：决策032（@6034-6038）定义 `on_track` / `falling_behind`（断签≥7天）/ `at_risk`（数学追不回），**未提** `slightly_behind`、**未提** `will_overdue`。
- 决策081（@4400-4406）已拍板：状态阈值以032/049/050为准，PRD §5.9.3 旧分级**取代、不再权威**；两态去留明确列入延后-27（检查081@4420）。
- `slightly_behind` 的唯一出处是**已被取代**的 PRD §5.9.3 算法A/B（1周未达标 / 近15天11-12天）。requirements_master@165 仍把状态机写成"4级含 slightly_behind"，但这与 PRD §5.9.2（7态含 will_overdue）本身就打架，属旧文档残留。
- `will_overdue`（将超期）仅在 PRD §5.9.2 作为枚举列出，但 §5.9.3 三套算法**从不产出它**——是 PRD 内部的"孤儿态"，无触发算法。其"将超期"语义已被决策032 的 `at_risk`（"按当前进度无法在截止日前完成"@6038）吞掉。
- "截止日临近"推送**独立成立**：决策068（@4958）把它定义为 C 类推送事件（due_date−7天 且 进度落后），自带触发条件，全程不引用任何名为 `will_overdue` 的状态。
- 决策107（@3454）事实上已按"两态 falling_behind/at_risk"叙述，把 slightly_behind/will_overdue 视为已出局。
- **规格自标未定**：决策081 明写"两态去留 = 延后-27"，故这是待 PM 拍的点，而非既成定论。

**选项**
- **选项A｜两态全删**：状态收敛为032 的 3 态（on_track/falling_behind/at_risk，另加 completed/paused 生命周期态），slightly_behind 与 will_overdue 都不实现。→ 与所有已定口径对齐、实现最简；代价是 requirements_master@165 "4级"需同步改3级，且失去"轻度落后"的黄色早期灰度。
- **选项B｜删 will_overdue、保留 slightly_behind**：给辅导员一档"橙前的黄"预警。→ 保住 master@165 的4级不改文档；但决策032 **从未定义** slightly_behind 阈值，保留=**必须新造一档阈值**（如断签3-6天），**触碰"不臆造阈值"铁律**，除非 PM 明确拍3-6天。且与决策107"两态"叙述不一致。
- **选项C｜两态全删 + 明文钉死 will_overdue 只是推送信号**：状态机同选项A的3态，同时在延后-27 落一句显式说明——"截止日临近"只是决策068 的 C 类推送事件，不对应任何状态枚举。→ 比A多一句收口，但正好正面回答本点要求的"will_overdue↔推送关系"，杜绝它日后被当状态复活。

**推荐 + 理由｜选C。** 依据链最硬且正面回答本点两问：(1) 去留——032 权威阈值只列3态、107 已按两态叙述、slightly_behind 唯一出处已被081取代，删两态是**顺着已定方向**而非新造；反之保留 slightly_behind 要臆造一档032未定义的阈值（B的硬伤）。(2) 关系——will_overdue 语义已被 at_risk 吞掉，而"截止日临近"在决策068 本就是自带触发条件的 C 类推送、不需状态载体，故应定性为"推送信号而非状态"。C 相对 A 只多一句显式收口，恰好闭合本点要求的关系。**落地须同步一处文档**：requirements_master@165 "4级(含 slightly_behind)"改为3级。

## DEF-2 · `at_risk`「数学追不回」的精确公式（daily / weekly / total_target+end_date 三型）

**规格现状（带出处）**
- 决策032（@6038）给出 at_risk 唯一文字定义："剩余天数 × 日均目标 < 剩余量（数学上追不回）"，日均基准 = 愿的 `daily_target`（@6042）。完整公式 reconciliation 明确列为延后-27（决策081@4405）。
- **三型逐一核对**：
  - **daily 型**（每日型，如净土/百字明/终身愿）：多为"终身、无总量、无截止日"，**数学上根本不存在"追不回"的终点**。决策049（@5528）明示"净土无总量目标，仍只走断签判定"。→ 032 的乘法式**套不进来**，规格上自标不适用。
  - **weekly 型**（入行观修）：决策050（@5496）**明确特判**——"按周目标，无法用总量剩余算 at_risk；改为：本周已过≥4天且本周座次=0 → falling_behind"（注意落点是 **falling_behind，不是 at_risk**）。→ 规格上**明确不产出 at_risk**。
  - **total_target+end_date 型**（如顶礼10万/2年、加行累计）：这是032乘法式**唯一真正适用**的类型。
- **矛盾/缺口（如实标）**：① 032 写"日均目标"但 total 型不一定填 daily_target，基准是"历史实际速度"还是"愿设定 daily_target"未明说（@6042偏后者，但 total 型该字段常为空）；② PRD 算法C（@949）是"C1累计比 + C2持续性 取更严重"双维，与032单一乘法式口径不同，reconciliation 未做；③ 起修豁免（PRD §5.9.4@955"起修7天内强制on_track"）与032未合并；④ 决策107 要求并入"觉学5维滞后快照"，但落表方案见 DEF-4。

**选项**
- **选项A｜只给 total 型定公式，daily/weekly 如实标"规格不适用"**：total 型给可判对错的线性外推式；daily/weekly 本就无总量终点（049/050已明说走断签或 falling_behind 特判），不臆造。→ 完全贴合已定决策、不越铁律；代价是需请 PM 确认"daily 型不再有 at_risk"（与 PRD 原7态不完全对齐）。
- **选项B｜三型都给公式，daily/weekly 借 PRD §5.9.3 算法B/A 的达标率反推**：覆盖 PRD 原7态。→ **直接违反**决策081（旧分级不再权威）与决策050（weekly 只落 falling_behind），且要照抄已被作废的阈值（<8/15天）或新造阈值，**臆造、不推荐**。
- **选项C｜本点整体不定**，只固化"total 型公式待 PM 在两个候选口径间选"，连同起修豁免/5维快照一并留延后-27。→ 最忠实于"实现期理清"、不越权；代价是本轮**不产出可落地公式**，实现仍被阻塞。

**推荐 + 理由｜选A。** 它是唯一"既给出可判对错的公式、又不违反任何已定决策"的路径。(1) total 型是032乘法式唯一真正适用对象，可落地为："按当前速度到截止日仍差量"即 at_risk，并叠加"剩余天数>0"与"起修豁免窗内强制 on_track"两个前置条件（具体计算式属实现细节，本简报不展开）。(2) daily 型据决策049、weekly 型据决策050，规格已明说不走总量式 at_risk，如实标"不适用"而非臆造，恪守铁律。**须请 PM 拍板两处口径**（属032↔PRD算法C 的真实冲突，不由调研自行消解）：
- **口径①**：total 型的"日均基准"取"**历史实际速度**（已修量÷已过天数）"还是"**愿设定的 daily_target**"？（032@6042偏后者，但 total 型该字段常为空，偏前者更可算。）
- **口径②**：是否采用 PRD 算法C 的"累计比 + 持续性 取更严重"双维？（本推荐先取单一累计维，持续性维并入 DEF-3 与5维快照一起理。）

## DEF-3 · 三套算法（A weekly / B daily / C total+end）与决策032/049/050 如何合并成一套连贯 ruleset

**规格现状（带出处）**
- 方向已锁（决策081@4400、检查081@4419）：以032/049/050为准、PRD §5.9.3取代，完整合并=延后-27。
- **per-type 简化阈值原文**：032（@6034-6040，通用/total型）= falling_behind 断签≥7天、at_risk 数学追不回、两态可同时成立；049（@5515）= 净土 daily 型有每日遍数目标但关怀口径"仅断签"；050（@5496）= 入行 weekly 型（≥3座/周、周一清零、无总量），特判"本周过≥4天且0座→falling_behind"、无法算 at_risk。
- **各愿归哪型有明确依据**（决策048@3580-3583 + @5483，反复标注"加行048与入行050座次模型不同、勿混"）：**加行→C（有 total_target 累计型，套032两态）；入行→A weekly（050特判）；净土→B daily（049仅断签）；百字明/顶礼等终身量→B/C**。
- **关键重构（会改变"合并"的形态）**：决策107（@3454，2026-06-15，晚于081）把管理端关怀名单改采觉学"5维滞后快照"（出勤/日常功课/听课/答题/观修），原文称"等于用觉学5维**实现/增强** sss 状态机"。落表 cohort_lag_snapshot（见 DEF-4）。→ per-vow 两态 与 per-person 5维lag **两套管理端产出并存**，合并前须先定二者关系（即 DEF-4）。
- **规格自标未定/矛盾**：slightly_behind/will_overdue（见 DEF-1）；起修豁免统一表述（见 DEF-5）；净土 daily 型的 at_risk（见 DEF-2）；出勤维 attendance_lag 阈值——决策180（@1350）**白纸黑字标"唯一真未定（规格自标）"**，即便走5维路线该维阈值仍未定（另见延后-5 升学量化门槛）。

**选项**
- **选项A｜合成一套 per-type 状态机 ruleset（3态）**：保留 per-vow 状态机，弃 slightly_behind/will_overdue，每型判定 = 加行C(032两态)/入行A(050特判)/净土B(049仅断签)，起修豁免统一为最高优先级 on_track。→ 直接兑现081简化方向、每型都能追到原文、改动最小；代价是删 will_overdue 后决策068"截止日临近推送"需补一个纯派生触发条件（属新增算法、须 PM 认可），且未落107的5维。
- **选项B｜以107 5维快照为准，per-vow 状态机降级为"观修维"输入之一**：管理端只维护一套 cohort_lag_snapshot。→ 与最新107对齐；代价是**出勤/听课/答题/日常功课4维的阈值多数无原文**（attendance_lag 决策180明标未定），摊开会暴露一批新未定点，**超出本子点范围**。
- **选项C｜分层**：per-vow 状态机(3态)作数据底座，107 5维作管理端展示聚合层，两决策都不推翻。→ 各司其职、不推翻任何决策；代价是实现两套计算+一层映射（最重），且"单愿态如何聚合成班级5维lag"本身又是新算法、须 PM 定，进一步扩大延后-27 工作量。

**推荐 + 理由｜选A 作为"三套算法合并"这一子点的默认成案，但须在延后-27 一并请 PM 拍板它与107 5维的关系**（因107晚于081、且明确要"用5维实现/增强状态机"）。理由：A 直接落实081已定简化方向，每型判定都能追到 032/049/050+048 原文、无臆造。**须 PM 显式补认可的仅一点**：删 will_overdue 后，决策068"截止日临近推送"的替代触发条件（这点不能默默假设，需摆到台面）。5维（107）与 attendance_lag 公式（决策180@1350 自标未定）属更大范围，建议在延后-27 里作为"A 之上的展示层归属"**单列**，不在本子点强行定清，避免臆造4个新维阈值。

## DEF-4 · per-vow `current_status` vs 关怀5维 `cohort_lag_snapshot` 的关系（v1.0 建哪个）〔最关键·先裁〕

**规格现状（带出处）** —— 这条几乎已被规格判成"并存、各管一层"，不是二选一，且两表两列都已实建：
1. **per-vow 状态机保留**：决策081（@4400-4405）以032/049/050为方向、状态机作管理工具保留不阻塞；schema_phase1@1486-1490 与迁移 20260618000060_practice.sql 里 `user_practice_vows.current_status` 列**实存**（粒度=每条愿一行、存算出的状态）。
2. **5维快照是"增强"不是"取代"**：决策107（@3454）原文"等于用觉学5维**实现/增强** sss 状态机"；检查107（@3475）"管理端两态→觉学5维（增强）；师兄端无状态色不变"。用词是**增强**、非取代（粒度=每(cohort,user)一行、5维、每日重算覆盖不留历史）。
3. **PM 已就"并存"拍板落 DB**：db_alignment_v2.md@189/198/201（**PM 批准 2026-06-16**）把 cohort_lag_snapshot 作为域⑥**新增表**加入，且 RLS 红线@201 把 cohort_lag_snapshot + vow.current_status + care_followups **三者并列**为师兄端一律不可读——即三者是三个独立对象。迁移 20260618000085_care_and_events.sql@65-73 已实建 cohort_lag_snapshot 五列。
4. **两条独立后端计算**：backend_audit_plan@19-20/104 列为两个 cron——vow-status-cron 算 current_status、care-lag-cron 算 5维；审计@26 确认两者现状是"表/列在、算的那层没写"（空壳）。
- **分工可读作**：current_status = per-vow **修持愿达标状态**（032断签≥7/049净土仅断签/050入行本周4天0座）；cohort_lag_snapshot = per-学员**跨5维学修全景**（含出勤/听课/答题等愿以外维度），供关怀名单定位。
- **自标未定/矛盾（务必如实说）**：延后-27 未理清项全在此汇聚（枚举去留=DEF-1、算法合并=DEF-3、起修豁免=DEF-5、净土at_risk=DEF-2）；现状 schema CHECK 仍含 slightly_behind/will_overdue（schema@1488），与032三态**不一致**；决策107 未逐字规定 current_status 是否仍进关怀名单排序，也未定义5维各维 lag 的阈值/算法（**实现期空白**）；PRD §5.9.6@963-967 旧排序按 at_risk/falling_behind 愿数、107改为5维，两者合并规则未明写。

**选项**
- **选项A｜两者并存、各管一层，v1.0 都建**：current_status 保留 per-vow 达标态；cohort_lag_snapshot 承载管理端关怀5维全景。→ 完全贴合已拍板事实（081保留、107"增强"、db_alignment PM已批准两表并存、迁移都已实建），**零返工、零改红线**；代价是 v1.0 要写两条 cron（现均空壳），且 current_status 枚举/阈值 reconciliation（DEF-1/2/3）仍须实现期收口，否则两套口径会各自漂移。
- **选项B｜5维取代 per-vow 状态机（废 current_status）**：只维护一条计算链。→ **直接违背**决策107明文"增强"（@3454）与检查107"师兄端无状态色不变、管理端增强"（@3475）；且5维里无"单愿达标"粒度，废掉会丢失愿级关怀信号，还要改schema删列/改RLS、推翻已批准方案，**臆造成分高、不可取**。
- **选项C｜只建 per-vow 状态机、5维快照延后（v1.0 不建 cohort_lag_snapshot）**：v1.0 范围最小。→ **违背** db_alignment@198 已批准的域⑥新表（迁移20260618000085已建），且只靠 current_status（纯修持愿）无法支撑107要的"管理端5维定位"，**等于回退107**。

**推荐 + 理由｜选A（两者并存、各管一层）。** 这不是新提议，而是把已拍板事实说清：决策081保留状态机、决策107明文"增强"非取代（@3454/3475）、PM 于2026-06-16 已在 db_alignment（@189-201）批准两表并存并把二者并列为师兄端不可读，且两表两列在迁移中都已实建。分工=current_status 管 per-vow 修持愿达标态，cohort_lag_snapshot 管 per-学员跨5维学修全景供关怀名单。B/C 都要推翻已批准方案且违决策107。**真正待办不在"建哪个"，而在这条之下的 DEF-1/2/3/5**：把 current_status 枚举对齐032三态、三套算法合并、5维各维 lag 阈值/算法定义（现完全空白）、以及5维与 current_status 在关怀名单排序上的合并口径——这些须在实现期收口，否则两套 computed 状态会各自漂移。建议把这几点作为延后-27 的明确子项交付。

## DEF-5 · 起修豁免统一表述 + 关怀5维 `attendance_lag` 精确公式 + 触发计算时机

**规格现状（带出处）** —— 三块，逐块标：

**A. 起修豁免**（已定"存在+方向"、未定"统一表述"）：PRD §5.9.4@955"起修后7天内任何愿强制 on_track"是旧算法版规则；决策081@4406 保留其为合理规则但明确"表述并入延后-27统一"（检查081@4421 同标🕐）。**矛盾点**：豁免有两种语义混着写——(a) 决策081 括注"start_date 未到不算落后"=**未起修就不判**；(b) PRD@955"起修后7天内强制on_track"=**已起修但给7天缓冲**，二者不是同一件事。另 auto 愿"入班即建、起修日=入班当天"（决策010@449/461）+ "提前起修/改节奏无需审批、记 pace_history"（PRD@215/463）使 start_date **可变**，豁免须说清锚在哪个 start_date。**此点无算法冲突，纯表述收口**。

**B. attendance_lag 精确公式**（自标未定，且存储态/运行态口径不一致）：决策180@1350 白纸黑字"⚠️ **唯一真未定（规格自标）**：attendance_lag 精确公式；旁听计入口径已由181锁定为只算 formal"。即"**算谁**"已定（仅 formal 成员，决策180(2)@1345、181）、"**怎么算成数字**"未定。三层现状：① 存储层 migration 20260618000085@68 `attendance_lag int DEFAULT 0`（无公式注释）；② 运行层 lib/queries/care.ts@114 把它算成"出勤率%→三档"，阈值来自 lib/admin-thresholds.ts@7 `ATTENDANCE={ok:85,near:70}`，且该文件@1-4 **自标"v1.0 占位启发式、非事实源、没给量化门槛（延后-5）"**；③ 分母口径已定可复用（只计 tracks_attendance=true 场次·决策041/065/066；只计 formal 期·决策180@1333）。**关键张力**：决策032@6037 状态机用"连续断签≥7天"（**天数型**，天然匹配 int 列），而 care.ts 现用"出勤率%档"（**比率型**）——attendance_lag 到底是"断签天数"还是"出勤率反向档"，规格从未裁定（升学量化门槛整体也在延后-5挂起）。

**C. 触发计算时机**（已定，但有 v1.0 落地缺口）：PRD §5.9.5@957-961 + 检查032@6061 定四个时机——①打卡后立即重算该愿 ②周日凌晨 cron 全平台重算（封上周）③辅导员改 due_date→立即重算（写 audit_logs）④转正后重算（决策026/181）。检查081@4422 判触发时机"沿用✅"（**非延后项**）。**缺口**：cohort_lag_snapshot 设计为"Edge cron 每日算"（migration@64），但 care.ts@9 自述"v1.0 dev 无 cron→在线算"——故触发"设计已定"，但 cron 是否 v1.0 落地、还是靠读时在线算，是**实现选择**。

**选项**
- **选项A｜最小收口**：只统一表述 + 把 attendance_lag 定义为"**断签天数（与决策032对齐）**"，触发时机按 §5.9.5 原样、cron 缺口显式标"v1.0 读时在线算"。→ 与032"断签≥7天=falling_behind"和 int 列语义完全对齐、**不新增阈值、不碰延后-5**；起修豁免一句话统一为"锚定愿当前 start_date；未到=不判(NULL/na)，起7天内=强制 on_track"收掉双语义。代价：与 care.ts 现跑的"出勤率%档(85/70)"相反（需改 care.ts 或明确它只是 UI 分色、不等于存储值）；出勤率维度信息量比断签天数细，改断签会丢"来了但常缺席"的信号。
- **选项B｜保留现状比率型**：attendance_lag 存储改"出勤率反向档"，正式采纳 admin-thresholds 的 85/70 为事实源阈值。→ 零改运行逻辑、UI与存储一致、维度更细；**代价直接违铁律**——85/70 被源码@1-4 自标"占位启发式·非事实源·待教务定（延后-5）"、PM 未拍过，且与032"断签≥7天"主轴割裂（状态机走断签、5维走出勤率，两套阈值），反而加深延后-27 要消的不一致。**不推荐。**
- **选项C｜全量 reconciliation**：本轮连 DEF-1（两态去留）、DEF-3（三套算法合并）、will_overdue↔068推送 一起定。→ 一次把延后-27 全关；代价是**远超本点范围**（本点只含起修豁免+attendance_lag+触发时机），will_overdue↔068 需另拉决策068全文，工作量与风险外溢，且量化门槛卡在延后-5、强定阈值会再次臆造。

**推荐 + 理由｜选A（最小收口）。** (1) **铁律优先**——只有 A 不新造阈值：032@6037"断签≥7天"是 PM 已拍的唯一事实源阈值，把 attendance_lag 定义为"断签天数"是把 int 列对齐到已有决策、而非臆造；85/70 被源码自标占位、量化门槛挂延后-5，B 采纳它=违律。(2) 三块可分离，本点不含 will_overdue/推送/三套算法合并（那是延后-27 其他子项，即 DEF-1/DEF-3），C 越界。(3) 起修豁免统一表述可无争议收口为一句："**豁免锚定该愿当前 start_date；start_date 未到→不进任何 lag 判定（记 na/NULL），start_date 起7天内→强制 on_track / lag=0**"——同时覆盖 PRD@955 与决策081@4406 的两种语义，且兼容 start_date 可变（决策010@449 起修日=入班当天、pace_history@463）。(4) 触发时机按 §5.9.5@957 原样沿用（检查081@4422 已判✅非延后），只需显式记"v1.0 无 cron→读时在线算，cohort_lag_snapshot 由 cron 上线后回填"这一实现缺口（care.ts@9 现状），不改设计。**需 PM 拍板的仅一点**：attendance_lag 走"断签天数(A)"还是保留"出勤率档(B)"——这是全案唯一实质分叉，建议 A 以与状态机主轴统一。

## 裁定顺序建议

1. **先裁 DEF-4（最关键·地基）**——确认"per-vow 状态机 + 关怀5维快照 两者并存、各管一层"（推荐A）。这决定了状态机整套东西留不留、干什么用；其余 4 条都踩在它上面。依据链已很硬（决策081保留 + 决策107"增强"非取代 + PM 2026-06-16 已批准两表并存 + 迁移已实建），故 DEF-4 更像"请 PM 确认既成事实"，一经确认，下面才有稳固地基。
2. **再裁 DEF-1（状态枚举去留）**——删 slightly_behind/will_overdue、收敛为032三态（推荐C）。它给 DEF-2/DEF-3 划定了"状态机内到底有哪几个态"的边界。
3. **接着 DEF-3（三套算法合并）**——加行C/入行A/净土B 合成一套3态 ruleset（推荐A），并把"删 will_overdue 后决策068 截止日推送的替代触发"这一点显式提交 PM 认可。
4. **然后 DEF-2（at_risk 公式）**——只给 total 型定公式、daily/weekly 标"不适用"（推荐A），并请 PM 拍两处口径（日均基准取历史速度还是设定值 / 是否采 PRD 算法C 双维）。
5. **最后 DEF-5（起修豁免 + attendance_lag + 触发时机）**——最小收口（推荐A），全案唯一实质分叉是 attendance_lag 走"断签天数"还是"出勤率档"，建议走断签以与状态机主轴统一。

> DEF-1/2/3/5 内部相互也有轻依赖（DEF-1 的枚举边界喂给 DEF-2/3；DEF-3 的 will_overdue↔推送 与 DEF-1 呼应），但都从属于 DEF-4 这一地基。**全部裁定后，本批即可转入"判例先行 / 写测试"阶段。**
