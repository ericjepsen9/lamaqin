## 二、设计到底怎么设计的（状态机 + 关怀概览·带出处）

设计在本域分四块，均带出处。**唯一贯穿一致、且已在库落实的是「受众」**；其余三块都留有历史叠层未收口。

### 2.1 受众：状态机是管理工具、师兄端零呈现（唯一稳定层）
- 师兄**完全看不到**状态颜色 / 标签 / at_risk 警示，只看数字；状态机「是管理工具，不是给师兄的成绩单」——`prd §5.9.1@890-898`。
- 师兄红线：看不到自己的状态机 / at_risk / care_followups / 他人进度——`requirements_master 附录C.2@315`；爱心可读 falling_behind/at_risk + 关怀名单、可写 care_followups（师兄完全不可见）——`C.4@322-324`。
- RLS 已在库落实：`cohort_lag_snapshot`·`vow.current_status`·`care_followups` 师兄端一律不可读——`db_alignment_v2@201`；生产迁移 `20260618000085@96-126` 已落地（SELECT 限 `has_class_role(zhumai/aixin)`+admin，写 care_followups 要 `care_worker_id=auth.uid()`）。
- **此层前后一致且已固化**。

### 2.3 算法：官方明确「未实现·延后-27」；线上另用觉学 5 维在线算顶替
- **完整算法悬空**：`prd §5.9.3@924-952` 三套算法（每周型连续未达标周数 / 每日型近 15 天达标天数 / 总量型 C1 累计 + C2 持续取更严）与 §5.9.4@953-955「起修后 7 天豁免」的合并统一，整体推给延后-27，未实现（决策 081@4405 + 延后清单@72）。
- **v2.0 只给了阈值方向碎片**：032=断签 ≥7 天→falling_behind / 剩余天数 × 日均 < 剩余量→at_risk；049 净土每日型仅断签、无 at_risk；050 入行每周型特判「本周过 ≥4 天且座次 =0→falling_behind」。
- **决策 107@3454 反向补**：管理端关怀名单不用状态机两态，改用觉学 **5 维滞后快照**（出勤 / 日常功课 / 听课 / 答题 / 观修分列），落表 `cohort_lag_snapshot`（迁移 `20260618000085@64-76`）。
- **v1.0 代码另起炉灶**：`lib/queries/care.ts` **完全绕开 `current_status` 与 `cohort_lag_snapshot` 表**，改在线算 5 维——仅 attendance/task 真算（@30-50），content/quiz/meditation 硬编码 `'na'`（@10-11、@16-18），flagged = 任一可算维为 high；文件头注@8-11 明标「v1.0 dev 无 cron → 在线算；阈值未定 → 不臆造」。阈值集中在 `lib/admin-thresholds.ts@1-15`，自标「占位启发式·非事实源·待教务定」。

### 2.4 触发时机：prd 规范 vs 落地方式
- 规范：打卡后立即重算 / 周日凌晨 cron 全平台重算 / 改 due_date 立即重算——`prd §5.9.5@957-961`；决策 032 检查@6061 补「打卡、宽限 due_date、转正均触发重算」。
- 落地：改为 **Edge cron TS 计算·不埋 DB 触发器**（迁移 `20260618000060@6/144` 注释、`db_alignment_v2@189`）。
- **实测：`supabase/` 下无 `functions` 目录**——状态机 / 5 维 lag 的计算主体尚未实现；仅字段与枚举就位。v1.0 dev 无 cron，靠 care.ts 在线算兜底。

### 2.5 人工后果层（严守大纲精神·不 auto-gate）
- 「了解情况」= 爱心 / 辅导员看关怀名单 → 电话 / 线下跟进 → 写 `care_followups`（决策 032/033 双入口@6004-6009；迁移 `000085@20`；`requirements_master@163-166`「关怀·人工·不动」）。App 不依打卡 / 掉队自动推送催促。
- 「取消学员资格」= 纯人工：`class_members.status='left'` 只是 admin 手改的枚举值（迁移 `20260618000010@113`），无任何 trigger/function 自动置 left（`requirements_master@161`）。
- 「升学 / 毕业」= 人工判定：决策 017@755-758（admin 手动、不预设通过线）+ 决策 123@2836（5 维人工评 + 锚定最初正式班级）；迁移 `20260618000070@4`·`20260618000095@3/21` 代码级明写「不 auto-gate」。

### 3.2 🔵 超出大纲（产品决策·非问题）

> **本域最关键的判定题——「设计粒度（每日 / 每周自动）远细于大纲（每学期人工）」是超出还是偏离？**
>
> **裁定：超出（产品化增强），不是偏离。** 三条理由，逐一给出可追溯依据：
> 1. **后果动作守住大纲红线**：大纲的硬约束在"结果"侧——取消资格 / 升学 / 毕业必须人工判定。设计把这三个动作全部保持人工、代码级明写「不 auto-gate」（见 S1）。高频侦测只服务于"更早发现、辅导员定位关怀重点"，不触发任何自动后果。**方向与大纲一致**。
> 2. **粒度是"更细 / 更勤"，不是"更松"**：大纲要求每学期至少看一次「未报或滞后严重」；设计做成每日 / 每周持续侦测多维滞后。方向是加密不是放松，不存在"漏掉大纲要求"的风险。
> 3. **有明确产品决策依据**：`requirements_master §0@22` 要求「大纲未细化处 = 产品决策需注明依据」。此处依据 = 决策 107@3454「5 维滞后快照比 sss 两态更细、利辅导员定位关怀重点」+ `prd §5.9.1@892`「状态机是管理工具」。**符合 §0 的产品决策程序**。
>
> 结论：属"超出大纲的产品化增强"。**但请注意**——"超出"是对"方向 / 性质"的判定；这不掩盖第四节所列的多处**内部收口问题**（枚举 / 算法 / 承载体 / 红线均未统一）。方向合规 ≠ 规格已定。
